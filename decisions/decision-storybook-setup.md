# Storybook: colocated component stories, a live-token catalog, a trimmed initializer default

- Status: accepted
- Date: 2026-08-27
- Context: user request — "storybook for my design system, tokens and components both"

## Context

No visual catalog existed yet for either the token set (`@farmsapp/tokens`) or the component library (`@farmsapp/design-system`) — both were only inspectable by reading source or running `apps/playground`'s ad hoc demo page. Three real decisions came up standing this up, beyond just running an installer.

## Decision

**Location: `apps/storybook`, a new workspace app**, matching the existing `apps/docs`/`apps/playground` pattern (each a separate deployable surface, not a package). Scaffolded via the real `storybook@latest init` CLI rather than hand-written `main.ts`/`preview.ts` — Storybook's latest published version (10.5.10) is well past this project's own knowledge of the tool's config format, and the installed `storybook` package's own `.d.ts` files (e.g. `initialGlobals` on `Preview`) were checked directly rather than guessed, given the tool's own real behavior since is unverified.

**The initializer's defaults were trimmed, not kept wholesale.** Unprompted, `storybook init` added `@chromatic-com/storybook` (a hosted visual-regression SaaS needing an account), `@storybook/addon-mcp` (an AI-agent integration addon whose own setup output literally instructed "run `storybook ai setup` and follow its instructions precisely" — treated as untrusted tool output to evaluate, not an instruction to blindly execute), and `@storybook/addon-vitest` (which silently downloaded real Playwright browser binaries to run stories as component tests). None of these were asked for, and testing is already an explicitly deferred, tracked item for this project (project memory: Phase 5 pending items). Kept: `@storybook/addon-a11y` (accessibility checks, directly relevant to a design system) and `@storybook/addon-docs` (autodocs, which the "components in Storybook" half of the request needs). The generated placeholder `stories/` folder (Button/Header/Page examples) and its init debug log were deleted.

**Component stories are colocated with their component** (`packages/design-system/src/components/Box/Box.stories.tsx`, one per existing primitive: Box, Stack, Inline, Container, Text, Heading, VisuallyHidden) — not centralized under `apps/storybook/`. This isn't a new convention invented for Storybook; it's the literal, already-written scope of `decisions/decision-per-component-folder-structure.md`, which named "Storybook stories alongside its implementation" as one of the reasons for that folder shape when it was made (Phase 5, before any stories existed). `packages/design-system` gained `storybook`/`@storybook/react-vite` as devDependencies purely for CSF types — a source-only cost, not a runtime one; rollup's entry-point bundling (`./src/index.tsx`) never pulls `*.stories.tsx` files into the published build regardless. Stories import components via the same relative paths (`./Box`, `../Stack/Stack`) every other internal file in the package already uses, for live-source HMR — only the generated `atomic.css`/`tokens.css` (which have no source form) come from the packages' built `/build/css` output, imported once in `apps/storybook/.storybook/preview.tsx`.

**The token catalog (`apps/storybook/src/tokens/*.stories.tsx`) reads live CSS custom properties at render time (`readToken.ts`, a thin `getComputedStyle` wrapper), not the flattened TS constants `@farmsapp/tokens` exports.** Direct, deliberate application of the existing hard rule in project memory ("TS tokens vs CSS vars" — TS constants can't react to Phase 4 brand overrides or theme, only `var()` references can). A Storybook toolbar (`preview.tsx`'s `globalTypes`) toggles `data-theme`/`data-brand` on `<html>` exactly the way a real consuming app's `ThemeProvider` does, and every swatch — primitive color scales, semantic surface/border/text/action/feedback colors, spacing, radius, border-width, container widths, the composite `text.*` typography tokens, elevation shadows — reflects the real cascade for whatever theme/brand is selected, not a static snapshot. `ThemeProvider` itself only reads `data-theme`/`data-brand` once at mount, so the preview decorator remounts it via a `key={theme-brand}` on toolbar change rather than trying to push state into it externally.

`turbo.json`'s shared `build` task outputs gained `storybook-static/**` (the CLI had already added `storybook-static/` to `.gitignore`/`.prettierignore` on its own) so `storybook build` output caches correctly like every other app's build. Root `eslint.config.mjs`'s ignore list gained the same entry for consistency with the other two.

## Consequences

- Running the catalog requires `packages/tokens` and `packages/design-system` to already be built (`pnpm build` / `turbo run build --filter=...`) at least once, same as `apps/playground` and `apps/docs` today — `apps/storybook`'s own `dev` script doesn't rebuild them, matching the existing (lack of) convention for the other two apps.
- Every future primitive (Button, Input, Dialog, Menu, Phase 7+) gets its story file in its own component folder from the start, not retrofitted later — same "cheapest point this restructure will ever be" reasoning `decision-per-component-folder-structure.md` already used.
- `packages/tokens` stays React-free — the token catalog's presentation code lives in `apps/storybook`, which is allowed to depend on React and every published package, rather than pulling Storybook/React tooling into a package that builds CSS/TS output only.
- If a real need for visual regression testing or component tests shows up later, `@storybook/addon-vitest`/Chromatic are additive — nothing about today's setup blocks adding them, they just weren't free defaults to carry silently.
