# `variant`/`letterSpacing` extend the shared atomic-CSS config, but stay off Box's own prop surface

- Status: accepted
- Date: 2026-08-22
- Context: Phase 5 (Primitives), Chunk 04 — Text, Heading

## Context

`Text`/`Heading` need two new style props the atomic-CSS system doesn't yet know about: `variant` (the composite `text.*` typography tokens, compiling to the CSS `font` shorthand — confirmed against the real generated CSS: `--ds-text-display: var(--ds-font-weight-bold) var(--ds-font-size-900)/var(--ds-line-height-tight) var(--ds-font-family-body);`) and `letterSpacing` (the primitive `letterSpacing.tight/normal/wide` scale). Both compile to the exact same shape `TOKEN_SCALE_PROPS` already generates for `radius`/`borderWidth` (one CSS property, a direct `var(--ds-{category}-{step})` reference) — so mechanically, the natural move is extending the same config `atomicConfig.mjs` already provides, matching what was told to the user earlier the same day: "if a future primitive needs entirely new style props of its own, those get added to this same file... not a second, parallel atomicConfig.mjs."

The real question was narrower: should `variant`/`letterSpacing` become real props on `Box` itself (making any `<Box>` instance able to render typography directly), or should they stay exclusive to `Text`/`Heading`?

## Decision

**Added as a new, separate exported object, `TOKEN_TYPOGRAPHY_PROPS`, not merged into `TOKEN_SCALE_PROPS`.** `Box.tsx`'s `PROP_CONFIG` is built by iterating `TOKEN_SCALE_PROPS` directly — merging the new props in would make Box's own resolver silently accept `variant`/`letterSpacing` at the JS level even though neither would be part of `BoxOwnProps`' TypeScript surface, a backdoor rather than a real boundary. Keeping them in a separate object, imported only by `Text.tsx`/`Heading.tsx`/`resolveTypographyClasses.ts` — never by `Box.tsx` — makes the exclusion structural, not just a type-level convention that a future edit could quietly undo by merging the objects.

**Reasoning for excluding them from Box at all**, not just how: Box's real, evidence-backed scope (confirmed via the Blade `Box`/`Card` research earlier the same day) is layout plus basic visual styling — background, border, radius, text color. Typography styling is a more specific concern that only `Text`/`Heading` actually need; exposing `variant` on bare `Box` would let it render arbitrary typography without going through either dedicated component, undermining the reason they exist. Same reasoning already applied to keeping feedback colors off `backgroundColor` (`LEARNING.md`, Phase 5 Chunk 04 entry) — Box stays bounded to what every layout primitive needs, rather than accumulating every visual concept a future component might want.

**Mechanism for Text/Heading's own resolution:** a small shared file, `src/components/Box/resolveTypographyClasses.ts`, computes `variant`/`letterSpacing` class names directly via the same `className()` helper `atomicConfig.mjs` already exports, then passes the result through Box's existing, already-additive `className` prop. Nested under `Box/` rather than a new top-level location — matching Blade's own real, confirmed precedent of nesting shared mechanisms (`styledProps/`) under `Box/` even when non-Box components (`BaseText`) reuse them. Both `Text` and `Heading` share this one resolver rather than each duplicating the same logic (and the same Devanagari safety guard — `decisions/decision-devanagari-letter-spacing-guard.md`) independently.

## A real bug, caught before shipping, not hypothetical

`variant`'s first draft used CSS class prefix `"text"` — which collides with Box's *existing* `color` prop, which already uses prefix `"text"` for an unrelated concept (`TOKEN_COLOR_PROPS.color`, generating `ds-text-primary`/`ds-text-secondary`/etc. for `TextColor` steps). Regenerating the CSS produced no *visible* collision only because today's step names happen not to overlap (`primary`/`secondary`/`disabled`/`inverse` vs. `display`/`heading-lg`/...) — a "works by luck, not by construction" gap, the same shape as two other real bugs caught earlier this same day (`RESPONSIVE_PROP_KEYS` going stale; `borderColor`/`borderWidth`'s `border-style` bundling). Fixed by renaming `variant`'s prefix to `"font"` (matching the actual CSS property it sets, and structurally unable to collide with `"text"`) before it ever generated a colliding rule.

## Consequences

- 267 base CSS rules now (was 257 before Chunk 04 — 10 new: 7 `text.*` variants + 3 `letterSpacing` steps), 29 props total (was 27). Confirmed by regenerating and grepping the real output.
- `generatedValidSteps.mjs`'s `VALID_STEPS` picked up `text`/`letter-spacing` automatically, since both were added to the same `scaleSteps` map the generator already derives from real token JSON — no separate generation step needed, and `Text`/`Heading`'s own dev-mode variant validation reuses this exact artifact rather than a third copy of the same step lists.
- `atomicConfig.d.mts` needed `TOKEN_TYPOGRAPHY_PROPS` typed with its exact two keys (`{ variant: ...; letterSpacing: ... }`), not a loose `Record<string, ...>` — a loose record made every dot-access "possibly undefined" under this project's `noUncheckedIndexedAccess`, a real `tsc` error caught immediately on the first build after adding the new object.

## Update — `color` joined this object too, moved off Box entirely

The reasoning above ("Box's real, evidence-backed scope... is layout plus basic visual styling — background, border, radius, **text color**") turned out to be wrong about `color` specifically, caught the same day by a follow-up Blade comparison scoped narrowly to color (not the earlier Box/Card research, a separate question). Real finding: Blade's `BaseBox` has **no text-color concept at all** — only `backgroundColor`/`borderColor`. `BaseText` declares its own independent `TextColors` type from scratch, with its own resolver, sharing nothing with `BaseBox` except layout/spacing props (`StyledPropsBlade`, confirmed to exclude color/backgroundColor/borderColor from its field list). Box having a `color` prop wasn't validated by Blade's precedent; it was the opposite of it.

**Decision, reached deliberately, not by default:** restructure to match — `color` moved out of `TOKEN_COLOR_PROPS` (where it had lived since Chunk 02) into `TOKEN_TEXT_PROPS` (renamed from `TOKEN_TYPOGRAPHY_PROPS` to reflect the broader scope), alongside `variant`/`letterSpacing`. `Box`'s own `color` prop and its `TextColor` type were removed entirely; `TextColor` now lives in `resolveTypographyClasses.ts`. `Text`/`Heading` gained `color` as their own declared prop (previously inherited for free via `BoxOwnProps`), resolved through the same shared resolver and the same dev-mode validation as `variant`. Unlike `variant`/`letterSpacing` (which default to fixed values), `color` stays genuinely optional with no default — omitting it lets ordinary CSS inheritance carry an ancestor's color through, preserving the exact behavior Box's own `color` prop had before the move.

Weighed explicitly against the cost, not assumed to be free: `Box`'s `color` prop predated `Text`/`Heading` (Chunk 02) and was already used directly, with no `Text`/`Heading` involved, in nine places across `apps/playground`'s permanent gallery (`Section`'s title, `Label`, both `ColorGallery` swatch demos, the `ComposedExample` card's title and body, and the gallery's own root wrapper and page heading). All nine were migrated — `Section`'s title and the root page heading became real `Heading`s (they were always semantically headings, using `<Box as="h2">`/`<Box as="h1">` as a workaround), `Label` and the card copy became `Text`, and the root wrapper — which relied on `color="primary"` propagating through CSS inheritance to keep the whole page legible in dark mode — became `<Text as="div">` instead of `<Box>`, since only `Text` can set that inherited color now.

**A second, more serious bug found while fixing the first one:** removing `color` from `BoxOwnProps` didn't make `<Box color="primary">` a compile error — it kept typechecking, because React's own base `HTMLAttributes<T>` (in `@types/react`) declares a generic, non-standard `color?: string` attribute every HTML element inherits, listed under a literal "Non-standard Attributes" comment in React's own type definitions. `BoxProps<T>`'s `Omit` excluded `"style"` explicitly but not `"color"`, so removing `color` from `BoxOwnProps` let it leak straight back in from React's own types — untyped, unvalidated, and worse than a type gap: it would have rendered as a literal HTML `color` DOM *attribute* (not a CSS style), which has no visual effect on a `div`/`span` at all. A silent, invisible failure, caught only because a throwaway `@ts-expect-error` probe unexpectedly passed instead of failing — never assumed safe just because `BoxOwnProps` itself looked correct. Fixed by adding `"color"` to the `Omit` exclusion list on `Box`, `Stack`, `Inline`, and `Container` (`Text`/`Heading` were already safe — they declare `color` in their own `OwnProps`, so `keyof OwnProps` already excluded it).

Re-verified end to end: full fresh `turbo run build lint typecheck --force` (19/19) after both the restructure and the `Omit` fix; a real `@ts-expect-error` probe confirmed `Box`/`Stack`/`Inline`/`Container` now genuinely reject `color` while `Text`/`Heading` still accept it; a real browser check (`playwright-core`/Edge, both themes) confirmed every migrated gallery usage renders with the correct computed color (title vs. body text distinguishably darker/lighter, the danger swatch still resolving to the exact `#720309` token value) and the root wrapper's dark-mode legibility workaround still works identically via `Text` instead of `Box`.
