# Learning Notes

A running log of what's being built in this repo, and — more importantly — *why*, written for someone doing their first monorepo / design-system build. Updated after each chunk of work.

---

## Some vocabulary up front

- **Monorepo** — one git repository containing many separately-installable packages (instead of one repo per package). This repo will eventually contain 7+ npm packages plus 2 apps, all versioned and tested together.
- **Package manager** — the tool that downloads your dependencies and manages `node_modules`. We're using **pnpm** (see Chunk 1 below for why, not npm's built-in one).
- **Workspace** — a package manager's term for "a monorepo it understands." `pnpm-workspace.yaml` tells pnpm which folders are packages.
- **Task runner / build orchestrator** — a tool that runs commands (build, lint, test) across many packages in the right order and skips work that hasn't changed. We're using **Turborepo**.
- **Bundler** — a tool that takes your source `.ts`/`.tsx` files and produces the actual files that get published to npm (or shipped to a browser). We're using **Rollup** for packages, **Vite** for the playground app, and **Next.js**'s own bundler for the docs app.

---

## Chunk 1 — Toolchain foundation

**Why:** Before any real code exists, the repo needs to agree on *how things get run*. Without this, every package would reinvent its own build/lint setup, and nothing could be run consistently across all of them at once.

**What we did:**
- `git init` — started version control.
- Installed **Node.js 24 (LTS)** and **pnpm 11**, and *pinned* both versions in files (`.node-version`, the `packageManager` field in `package.json`) so every contributor's machine — and CI later — uses the exact same versions. Without pinning, "works on my machine" bugs creep in from version drift.
- `pnpm-workspace.yaml` — tells pnpm "everything under `apps/` and `packages/` is a workspace member."
- `turbo.json` — defines the task pipeline (`build`, `lint`, `typecheck`, `test`) and, critically, `dependsOn: ["^build"]`, which tells Turborepo "before building package X, build everything X depends on first." This is what makes builds happen in the correct order automatically.
- `tsconfig.base.json` — one shared, strict TypeScript config every package extends, so type-safety rules are consistent everywhere instead of each package deciding its own.
- `.gitignore`, `.prettierrc.json` — housekeeping: don't commit `node_modules`/build output, and agree on code formatting.

**Gotcha we hit:** The installed Node (20) turned out to be past its official support window (end-of-life), and was also too old for the current version of pnpm to even run. Fixed by installing Node 24 via `winget` (Windows's package manager) instead of trying to force an old pnpm to work.

---

## Chunk 2 — Shared lint & style configs

**Why:** "Components must not hard-code brand colors" is a rule from the architecture doc — but a rule that's only written in a doc gets ignored under deadline pressure. Turning it into a *linter rule* makes it a build failure instead of a suggestion.

**What we did:**
- `packages/eslint-config` — a real npm package (not published, just workspace-internal) containing our shared ESLint rules. Split into a base config (for plain TypeScript packages) and a `/react` variant (adds React/JSX/accessibility rules) — so a package like `tokens` that has zero UI code isn't forced to install React-related tooling it doesn't need.
- `packages/stylelint-config` — same idea, for CSS. The key rule here is `stylelint-declaration-strict-value`, configured to reject any raw color value like `color: #ffffff` and only allow `color: var(--ds-something)`. We proved this actually works by writing a throwaway CSS file with a raw hex color and confirming Stylelint flagged it, then deleted the test file.

**Gotcha we hit:** Our first version of the ESLint config didn't know about Node.js's built-in globals (`module`, `require`, etc.), so it broke on `.cjs` config files. Real bug, fixed by explicitly telling ESLint which "environment" (Node vs. browser) each file type runs in.

---

## Chunk 3 — Shared build tooling + package generator

**Why:** Every package needs a build config, but writing one from scratch 7+ times both wastes time and *guarantees* they'll drift apart from each other over time. We wrote it once and made every package reuse it.

**What we did:**
- `tooling/build/rollup.config.base.mjs` — one shared Rollup configuration (Rollup is the tool that compiles TypeScript source into the `.js` + `.d.ts` files that actually get published). Every package's own tiny `rollup.config.mjs` just calls into this shared file with its own entry point.
- `tooling/generators` — a `plop` generator: run one command, answer two questions (package name, does it need React?), and get a fully-wired new package instantly, instead of copy-pasting an existing one and forgetting to rename something.

**Gotcha we hit (a real lesson about how tools resolve paths):** A shared config file that lives *outside* any package (like `tooling/build/rollup.config.base.mjs`) resolves its own `import` statements relative to *its own location on disk*, not relative to whichever package happens to be using it. This meant the Rollup plugin packages had to be installed at the *repository root*, not inside each individual package — a subtle but important rule about how Node.js resolves modules. We also hit the same "resolves relative to itself" surprise with the `plop` generator's file paths, twice, and only caught it because we tested the generator for real instead of assuming it worked.

## Chunk 4 — First real package, proven end-to-end

**Why:** Before repeating a pattern 6 more times, prove it actually works once. This is cheaper than discovering a fundamental problem after building 7 packages the same (broken) way.

**What we did:**
- Generated `packages/tokens` — the first package, chosen because nothing else depends on anything, so it's the simplest possible test case.
- Actually ran `pnpm install`, `turbo run build`, `turbo run lint`, `turbo run typecheck` — and inspected the *real output files* (not just "did the command exit successfully") to confirm Rollup produced a correct `.js` file and a correctly bundled `.d.ts` type-definition file.

**Gotcha we hit:** Turborepo needs to run the `pnpm` command internally, but `pnpm` wasn't available as a plain command on this machine (a Windows permissions issue — installing global command shortcuts normally needs administrator rights). Fixed by pointing Corepack (Node's built-in tool-version manager) at a folder the current user *can* write to.

## Chunk 5 — The remaining six packages

**Why:** With the pattern proven, replicate it — but the interesting part isn't the repetition, it's getting the *dependency wiring* right, since that's what makes `turbo run build` build things in the correct order automatically.

**What we did:**
- Generated `themes`, `utilities`, `primitives`, `components`, `icons`, `design-system` via the same generator.
- Hand-wired each package's real dependencies to match the architecture doc's rules — e.g. `primitives` depends on `tokens` + `utilities`; `components` depends on `primitives` + `utilities`; the `design-system` meta-package re-exports `components` + `primitives`. We deliberately did *not* add the Radix/Floating UI libraries yet, even though the architecture doc names them, because nothing uses them yet — adding a dependency before it's needed is exactly the kind of thing that bloats a project over time for no benefit.
- Verified: `turbo run build` built all 9 packages in the correct dependency order automatically (you can see this in the logs — `tokens` builds before `primitives`, which builds before `components`, which builds before `design-system`).

## Chunk 6 — The two apps

**Why:** `apps/playground` is a scratch space to try out components as they're built (rather than testing them inside a real product). `apps/docs` will eventually be the public documentation site. Both need to exist as real, buildable apps — even mostly empty ones — so the workspace's build pipeline covers 100% of the repo, not just the library packages.

**What we did:**
- `apps/playground` — a minimal Vite + React app. Builds to a real, deployable bundle.
- `apps/docs` — a minimal Next.js app (the App Router style, which is Next's current recommended approach). Produces a real static production build.

**Gotchas we hit (both real bugs, both fixed):**
1. Next.js generates its own `next-env.d.ts` file automatically, and that file intentionally uses a coding pattern (a "triple-slash reference") that our lint rules flag as an error elsewhere. Since it's a file Next.js owns and regenerates, not one we write, we told ESLint to skip linting it rather than fighting Next's own convention.
2. Next.js's image-optimization feature depends on a native (non-JavaScript) library called `sharp`, which pnpm 11 refuses to auto-install for security reasons (it blocks any dependency's install-time scripts by default, and makes you explicitly approve them) — we reviewed and approved it, the same way we did for `esbuild` earlier.

## Chunk 7 — Changesets + CI

**Why:** Two separate problems, both about to bite us once more than one person touches this repo:
1. *"What version number does this change deserve?"* — Left to guesswork at release time, this always turns into either arguing over semver or someone just bumping randomly. **Changesets** fixes this by having each PR include a tiny markdown file describing its own change and severity (patch/minor/major) at the time the change is made, when the author still remembers what they did.
2. *"Does every change actually get verified before merging?"* — Right now, the whole toolchain only gets checked when *we* remember to run it by hand. **CI** (Continuous Integration — an automated pipeline that runs on every pull request) makes that automatic and unskippable.

**What we did:**
- `.changeset/config.json` — configured Changesets, including one workspace-specific rule: `apps/docs` and `apps/playground` are excluded from versioning, since they're internal apps, not published packages — versioning them would be meaningless.
- `.github/workflows/ci.yml` — a GitHub Actions pipeline that runs on every pull request: install → lint → typecheck → build → test, in that order (cheapest/fastest checks first, so a typo gets caught in seconds, not after a 2-minute build).
- `.github/workflows/release.yml` — the publish pipeline. When changes land on `main`, this either opens a "Version Packages" pull request (bundling up all the pending changesets into real version bumps) or, once that PR is merged, actually publishes to npm. It uses **npm Trusted Publishing** (an npm feature that authenticates the GitHub Action directly, so there's no long-lived secret password stored in the repo that could leak).

**Gotcha we hit:** Our config said `baseBranch: "main"`, but `git init` had created a branch called `master` (an older default that some git installations still use). A mismatch like this wouldn't cause an error until someone actually tried to release — we caught and fixed it now by renaming the branch, before it became a problem nobody noticed until release day.

**Note:** These two workflow files are written correctly, but nothing has actually *run* them yet — that requires a GitHub remote (a repo pushed to github.com), which doesn't exist yet for this project. Also, real publishing won't work until the npm side of Trusted Publishing is configured once, manually, on npmjs.com — that's a one-time setup step for whoever owns the `@farmsapp` npm org, not something this repo's code can do on its own.

## Chunk 8 — Exit-criteria verification

**Why:** Every earlier chunk was verified on its own, in isolation. That's not quite the same as proving the *whole* Phase 1 scaffold works together, from a clean state, the way a new contributor (or CI) would actually experience it. This chunk closes that gap.

**What we did:**
- `pnpm install --frozen-lockfile` — the flag CI uses. It fails loudly if the lockfile and any `package.json` have drifted apart, so this proves everything is genuinely in sync, not just "works on this machine right now."
- `turbo run build lint typecheck --force` across the whole repo — the `--force` flag skips Turborepo's cache, so this was a fully fresh run, not one coasting on results from earlier chunks.
- The big one: actually exercised the **Changesets version-bump mechanism** for real, instead of just checking that its config file is valid. We wrote a real changeset file (a small markdown file describing "bump `tokens` by a patch version"), then ran `changeset version` for real. It correctly:
  - Bumped `@farmsapp/tokens` from `0.0.0` → `0.0.1`
  - **Cascaded that bump** to every package that depends on tokens (`primitives`, `themes`, `components`, `design-system`) — but correctly left `utilities` and `icons` alone, since neither depends on tokens. This is the dependency-graph awareness from Chunk 5 showing up again, now inside the release tooling itself.
  - Generated a real `CHANGELOG.md` per package, with the changeset's description as the entry.
- Since this was a *proof*, not a real release (these are still empty placeholder packages — bumping their version means nothing yet), we reverted all of it afterward: `git checkout` on the version-bumped `package.json` files, deleted the generated changelogs, deleted the probe changeset. Then rebuilt once more to confirm the repo was back to a clean, working state.

**The pattern here, worth noticing:** this is the same "prove it, then clean up" approach used earlier for the Stylelint rule (Chunk 2) and the package generator (Chunk 3) — verify a mechanism actually works by really running it against disposable input, rather than trusting that correct-looking config *must* behave correctly.

**Phase 1 is now complete** against the roadmap's own exit criteria: an empty monorepo that builds, lints, typechecks, and can version/publish end-to-end.

# Phase 2 — Primitive Tokens

Per the Token Foundation roadmap. Same chunked approach as Phase 1.

## Chunk 01 — Style Dictionary pipeline

**Why:** Before authoring a full color/type/space scale, prove that a token goes in one end and comes out the other correctly — as both a real CSS custom property and a real typed TS constant — using one throwaway value. Authoring 60+ real values against an unproven pipeline would mean redoing all of it if the pipeline itself had a problem.

**What we did:**
- Installed **Style Dictionary** (the tool that reads token source files and generates output in whatever formats you need) into `packages/tokens`.
- Authored one dummy token, `color.blue.500`, in `packages/tokens/tokens/color.json`, using the **W3C DTCG format** — a standardized way of writing design tokens as JSON (`$value`, `$type` keys) that's also what a future Figma sync would expect, so we're not picking a format now that has to be migrated later.
- Wrote a Style Dictionary config defining two outputs from that one source file: a CSS file (`build/css/tokens.css`, real custom properties like `--ds-color-blue-500`) and a generated TypeScript file (`src/generated/tokens.ts`, a real typed constant) that Rollup then bundles normally, exactly like every other package already does.
- The generated TS file is **build output, not source** — regenerated every build, never hand-edited, and added to `.gitignore` accordingly (same treatment as any other compiled output).

**It worked correctly on the first real run** — genuinely rare in this project so far, and worth noting as a contrast to the earlier chunks that each caught a bug. Inspected the real output by hand anyway rather than trusting a clean exit code: the CSS variable name, the TS constant, and the final bundled export were all exactly right.

**Extra verification, beyond what the roadmap asked for:** changed the dummy token's value and confirmed Turborepo's cache correctly detected it as a change and rebuilt (rather than serving a stale cached result) — this matters because a caching bug here would mean token *value* changes could silently fail to propagate, which would be a nasty, hard-to-notice class of bug later.

## Chunk 02 — Lint boundary for generated CSS

**Why (as originally planned):** Phase 1 built a Stylelint rule rejecting raw hex colors in hand-authored CSS. The worry was that the newly-generated `tokens.css` — which legitimately *contains* raw hex values, since that's where a token's real value has to live — would trip that same rule.

**What actually happened, and the correction worth recording:** it didn't trip the rule. Testing it for real (not just assuming) showed the strict-value rule only checks specific *standard* CSS properties (`color`, `background`, etc.) — a custom property declaration like `--ds-color-blue-500: #2b5a9e` has a property *name* of `--ds-color-blue-500`, which doesn't match any of those patterns, so the rule was never actually at risk here. This is a case where a prediction made in the roadmap turned out to be wrong once actually tested — worth being honest about rather than quietly writing the roadmap's original reasoning into history as if it had been correct.

Still added the exclusion anyway (`.stylelintignore`, excluding `**/build/**`), but for a better reason: build output shouldn't be linted as a general policy regardless of whether it happens to currently pass, since it's regenerated output nobody's meant to hand-fix if flagged, and future changes to the pipeline could introduce something that *does* get flagged.

**Gotcha this surfaced:** once `build/` was excluded, there was briefly *zero* hand-authored CSS anywhere in the repo (the only CSS that existed was the generated one) — which made the lint command hard-error with "no files found," since that's a genuinely different situation from "found files, no problems." Fixed by allowing empty input, which is the correct normal state until real component CSS exists in a later phase.

**Verification:** confirmed with a real throwaway test file that a genuine violation is still caught (same "prove it, then delete the test file" pattern used throughout this project) while the generated file is correctly excluded — checked that *exactly one* file was linted, not zero and not more than expected.

## Chunk 03 — Primitive color scale

**Why:** The roadmap flagged a real risk: the brand anchor (`#193921`) is already dark, so hand-picking 12 "lighter" shades by eye risked washed-out, muddy results. Lightening a dark, desaturated color correctly isn't just "add white" — it needs the color's actual perceptual lightness *and* saturation tuned per step, which means real color math, not guessing hex codes.

**What we did:**
- Wrote a reusable generator script (`packages/tokens/scripts/generate-scale.mjs`) using **OKLCH** — a color space designed so that equal numeric steps in lightness *look* like equal steps to the human eye, unlike RGB or HSL, where the same numeric change looks very different depending on where you start. It converts the brand anchor into OKLCH, builds a 12-step curve of lightness/saturation targets around it, and converts each step back to a real hex color.
- Generated four 12-step scales: **brand** (anchored to `#193921` at step 9, its "solid background" role), **neutral** (a very subtly brand-tinted gray), and raw **danger** (red) and **warning** (amber) scales — status hues only, not yet assigned any semantic meaning. Whether "success" reuses the brand green or gets its own hue is a semantic decision, deliberately left for Phase 3.
- Verified every text step (11 and 12, in every scale) actually passes WCAG contrast against white by computing the real ratio, not asserting it.

**A real design problem, caught and fixed before it shipped:** the first version of the brand curve produced steps 11 and 12 as `#01220b` and `#001204` — both nearly black, barely distinguishable from each other. The cause: forcing the anchor to land exactly on step 9 created one huge, uneven jump in the lightness curve (far bigger than any other step-to-step change), and that unevenness compounded going into the darker text steps. Fixed by re-shaping the whole curve so the deltas between consecutive steps stay smooth and comparable, with the anchor still landing exactly on step 9 but the surrounding steps built around it more evenly. This is exactly the kind of mistake that's easy to miss by only checking "does it pass contrast" (it did, even in the broken version) — worth checking whether steps actually look *distinct* from their neighbors, not just individually correct.

**Full pipeline proof:** ran the real Style Dictionary + Rollup build with all 48 real values, inspected the generated CSS (`--ds-color-brand-9: #193921;`, correctly prefixed and named) and TS constants by hand, then did a throwaway import of one token from `packages/primitives` to confirm a value actually flows from `tokens` into a consuming package end to end — reverted after, same pattern as every other chunk's proof.

**Small cleanup along the way:** the generator script's `console.log` calls tripped our own `no-console` ESLint rule (warnings, not errors) — that rule exists for library code we ship, not for a CLI script whose entire purpose is printing output, so added a scoped exception for `packages/tokens/scripts/**` rather than leaving lint warnings that would keep reappearing every time this script runs.

**A bug found before this entry was even written:** between finishing Chunk 03 and starting Chunk 05, `generate-scale.mjs` changed on disk with a typo (`s.step0p` instead of `s.step`) that would have silently corrupted every future run — all 12 steps of every scale would collapse onto a single `"undefined"` key, overwriting each other, leaving only the last one. The token file already on disk was unaffected (it was written before the typo appeared), but the *next* run would have broken it. Fixed, then verified the fix by re-running the script and confirming the output was byte-for-byte identical to what was already there — proof the fix didn't change behavior, just restored it.

## Chunk 05 — Spacing, radius & breakpoints

**Why:** Every layout primitive built in Phase 5 (Box, Stack, Inline) will be built on this grid — and the two locked decisions (8px base unit, two separate breakpoint sets) needed to actually become real, usable values.

**What we did:**
- A spacing scale on the 8px grid, denser at the commonly-used low end (8px, 16px, 24px...) and sparser at the high end (64px, 96px, 128px) — plus one deliberate exception, a 4px half-step for fine-grained cases like icon padding.
- Radius and border-width scales — small, fixed sets rather than open ranges (`radius.sm/md/lg/xl/full`, `borderWidth.thin/thick/heavy`).
- The two locked breakpoint sets (consumer: 600/900px; portal: 600/1280/1536px), which surfaced a real technical constraint worth understanding: **a CSS custom property cannot be used inside an `@media` condition.** Browsers require a literal value there — `@media (min-width: var(--x))` isn't valid CSS, full stop. So a breakpoint token is only ever usable as a JS/TS value (for `matchMedia()` checks or build-time responsive style generation), never as `var(--ds-breakpoint-...)` in a stylesheet. Style Dictionary's per-file `filter` option excludes breakpoints from the CSS output entirely, so there's no custom property sitting in `tokens.css` that looks usable but silently isn't.

**A real bug in the fix itself, caught by actually checking:** the first attempt put the `filter` at the wrong level of the Style Dictionary config (on the platform, not the individual output file) — it silently did nothing, and breakpoints still showed up in the generated CSS. Moving `filter` onto the file entry fixed it, verified by grepping the real output for both files: zero breakpoint matches in `tokens.css`, all five present in `tokens.ts`.

## Chunk 06 — Elevation, motion & z-index

**Why:** The remaining primitive categories, both already locked (snappy/utilitarian motion) or straightforward to define narrowly (a handful of shadow levels and named stacking layers, not open-ended ranges).

**What we did:**
- A 3-level shadow scale (`resting`, `raised`, `overlay`), some as single shadows and some as layered multi-shadow values — this is where DTCG's structured `shadow` token type mattered: Style Dictionary correctly serialized a JS array of shadow objects into valid, comma-separated CSS `box-shadow` syntax with no extra configuration needed.
- Motion primitives tuned toward the locked snappy/utilitarian direction: short durations (100/150/200ms) and restrained, mostly-linear easing curves rather than pronounced bounce/spring curves.
- A z-index scale using named layers (`base`, `sticky`, `overlay`, `modal`, `toast`) with roomy gaps between them (increments of 100), rather than arbitrary numbers two components might collide on.

**Verification, across both chunks:** full fresh `build`/`lint`/`typecheck` across the whole workspace (25/25), plus a throwaway import of a shadow object (not just a simple string token, to specifically test the more complex structured type) from `packages/primitives` — confirming both that the value flows through correctly *and* that TypeScript infers its object shape correctly, not just `any`. Also caught the same class of gap as Chunk 02: the root-level `eslint .` sweep didn't know about the `scripts/` console-output exception either, for the same underlying reason (flat-config ESLint doesn't cascade into subdirectory configs) — fixed once, generally, for any package's `scripts/` directory rather than patching it per-package each time it comes up.

## Chunk 04 — Typography scale

**A real conversation happened before any code, worth recording:** before picking a font, the question came up of *why the design system decides this at all* — shouldn't each app pick its own? The answer, worth restating here since it's a recurring architectural idea in this project: font is a brand-identity primitive in the same category as color, and the components that will actually render text (`Text`/`Heading`, built in Phase 5) will reference a token, never a literal font name — a rule already mechanically enforced by the Stylelint strict-value rule from Phase 1. That's what makes "what if consumer and portal need different fonts later" cheap to answer: the brand-override mechanism already planned for Phase 4 (§06's `data-brand` axis) would handle it without touching any component code, because the indirection is already there by construction. Locked typeface: **Noto Sans + Noto Sans Devanagari** (over Hind and Mukta) — the safest multi-script coverage guarantee.

**What we did:**
- `fontFamily.body` — a real, valid CSS font stack (`'Noto Sans', 'Noto Sans Devanagari', sans-serif'`) where the browser automatically falls back to the Devanagari face for Hindi text the base family doesn't cover, without any JS logic needed to switch fonts.
- `fontFamily.mono` — deliberately a **system font stack**, not a downloaded one (numbers/tabular data still need a monospace option, but adding a fourth font family to download would work against the low-end-device/weak-connectivity constraint already locked for motion).
- A 9-step font size scale (12px→36px, `fontSize.100`…`fontSize.900`) and font weight/line-height/letter-spacing scales — all hand-tuned to clean pixel values rather than raw ratio math, same practice as the spacing scale.

**A non-obvious catch worth remembering:** Devanagari is a connected/complex script — applying Latin-style letter-spacing (tracking) to it can visually break how the glyphs join together. The letter-spacing tokens are documented as Latin-only for this reason; whoever builds the `Text` primitive in Phase 5 needs to apply them conditionally, not uniformly to all rendered text.

**Verification:** confirmed the DTCG `fontFamily` array type (an actual array value, not a single string) serialized correctly into both a properly-quoted CSS font stack and a real TS array — genuinely correct on the first attempt, same as the shadow/cubicBezier types in Chunk 06. Also a real cross-type consumption proof: imported the array-typed `FontFamilyBody` from `packages/primitives`, confirming TypeScript correctly typed it as a string array rather than `any`.

## Chunk 07 — Full pipeline verification, Phase 2 close-out

**Why:** Same reasoning as Phase 1's Chunk 8 — prove the whole primitive tier together, from a clean state, not just each category in isolation.

**A real gap caught here, not earlier:** re-checking the roadmap's own exit criteria against the *original* project brief's token category list turned up something the roadmap itself had silently dropped — **focus states**. The brief calls it out as its own primitive category (alongside color, spacing, motion, etc.), and it's a first-class accessibility requirement elsewhere in the architecture doc, but it never made it into the Token Foundation roadmap's Chunk 07 exit criteria when that doc was first written. Caught by actually re-reading the brief against the plan rather than trusting the plan was complete, and fixed before calling Phase 2 done: added `focusRing.width` (2px) and `focusRing.offset` (2px) as primitive tokens. Deliberately *not* including a `focusRing.color` primitive — which specific raw color gets used for focus visibility is a semantic assignment (Phase 3's job), same reasoning as leaving "success" unassigned to a specific hue back in Chunk 03.

**What we verified:**
- Every category from the brief present in the real generated output, checked by hand: 105 CSS custom properties total, spanning color, shadow, focus, duration, easing, z-index, spacing, radius, border-width, font-family/size/weight, line-height, and letter-spacing — plus breakpoints correctly present in TS only, absent from CSS.
- `pnpm install --frozen-lockfile` — confirms the lockfile is genuinely in sync with every `package.json`, not just that things happen to work on this machine right now.
- Full fresh `turbo run build lint typecheck --force` across all 12 packages/apps: clean, 25/25, zero warnings.

**Phase 2 is now complete.** The primitive tier — every category the original brief listed — compiles to real CSS custom properties and typed TS constants, is consumable from another package in the dependency graph (proven repeatedly, once per token type shape: string, object, array), and the whole workspace still builds/lints/typechecks clean with real values in place instead of a placeholder constant.

## After Phase 2 — comparing against Razorpay's Blade design system

**Why:** Having just built a real token pipeline, it's a good moment to check it against a real, production design system's actual implementation — not to copy it wholesale, but to see which of our choices hold up under comparison and which don't. Dispatched a research prompt into a local checkout of Blade asking it to trace its complete token flow, evidence-first, the same way earlier Blade research informed the React Native planning in the System Blueprint.

**What the comparison actually validated, not just "confirmed we're different":**
- **OKLCH over HSL** — Blade's custom-brand-color generator uses HSL's `.brighten()`/`.darken()` (via `tinycolor2`), which is exactly the *naive lightening* failure mode the Chunk 03 roadmap specifically warned about and OKLCH was chosen to avoid. This isn't a hypothetical risk — it's a real limitation in a real, shipped design system's actual code.
- **Breakpoints as TS-only, never CSS variables** — the single most concrete validation in the whole comparison. Blade's `blade-core` *does* generate `--breakpoint-*` CSS custom properties, but grepping its own codebase for actual usage found that literally nothing uses them inside an `@media` condition — every real responsive rule hardcodes a literal pixel value instead, with a code comment explicitly acknowledging that breakpoint values get "baked into generated classes," not read from the variable. Blade generates the exact dead-weight custom property we deliberately chose not to generate.
- **Structured shadow tokens, a real z-index scale, the Stylelint hex-rejection rule** — Blade's shadows are flat pre-composed strings (despite a comment describing the intended field structure), it has no z-index token scale at all (just an ad-hoc per-instance prop), and no lint rule stops a raw hex value in component code. All three are places our Phase 1/2 investment produced something Blade's actual production system doesn't have.
- **The Phase 4 CSS-cascade theming plan (not yet built)** — both of Blade's frameworks re-derive and re-inject the active theme via JS/Context on every render or mount, and the Svelte provider has a documented, known SSR-flash risk as a direct cost of that approach. Our still-unbuilt Phase 4 plan (attribute-driven, cascade-resolved, zero re-render) is designed specifically to avoid that exact cost — good to know the plan holds up before it's even built.

**A genuine self-critique, not just validation:** Blade assigns color *roles* (border, background, text) entirely in its semantic layer — its primitive color scale carries no meaning at all. Our Radix-style 12-step convention bakes a little meaning into the primitive tier itself (step 9 is *designed* for solid backgrounds, step 11 for text) — which sits in real tension with our own stated rule that primitives should carry no meaning. Decision: keep it, since it's exactly what gives "which step is safe for text" a structural guarantee instead of a per-use judgment call — but this is a disclosed tradeoff, not a rule we get to pretend isn't bent. Worth re-checking when Phase 3 actually defines the semantic layer, so the tension doesn't quietly compound.

**Patterns worth borrowing later, saved to project memory so they don't get lost before their phase arrives (not relevant yet):**
- Phase 5 (Text/Heading primitives): Blade subsets its fonts per-script via CSS `unicode-range`, with fallback faces tuned via `size-adjust`/`ascent-override` to avoid layout shift before the real font loads — worth applying to the Noto Sans + Noto Sans Devanagari pairing.
- Phase 11 (React Native parity): Blade types its easing tokens as `Platform.Select<{ web: string; native: EasingFactoryFn }>` — same token name, a CSS `cubic-bezier()` string on web and a real `react-native-reanimated` easing function on native. This is exactly the problem our own motion tokens will hit once a native output exists.
- Phase 12 (white-label at scale, only if customers ever get live/dynamic brand-color generation): Blade runs WCAG contrast checks (`tinycolor.isReadable()`) at *runtime* against a customer-supplied anchor color, since it can't pre-verify contrast for a color it doesn't know in advance — different from our own build-time-only check, which only works because we know our own values ahead of time.

# Phase 3 — Semantic Tokens

Per the Semantic Layer roadmap.

## Chunks 01 + 02 — Structural color, action & interactive states

**Why:** These are the highest-frequency semantic tokens in the whole system — almost every future component reaches for a surface, border, text, or action color before anything else. Both chunks are pure color work with no dependency on the still-open success-color question, so they ran together.

**What we did:**
- `color.surface.*`, `color.border.*`, `color.text.*` — direct aliases to specific neutral-scale steps (e.g. `color.text.primary → {color.neutral.12}`), each with a stated reason for that specific step, not just "picked one that looked right."
- `color.action.primary` and its hover/active/disabled variants, resolving a real gap the primitive convention left open: there's no dedicated "pressed" step in the 12-step scale (9-10 are solid-background default/hover; 11-12 are reserved for text). Decision: `active` reuses `hover`'s value, and pressed-state feedback comes from motion (a scale/transform) instead of a third background color — cheaper than inventing a 13th primitive step, and revisitable later with a real component in hand if it turns out insufficient.
- `color.action.primary-disabled` deliberately does **not** alias a dimmed/opacity-reduced brand color — it flattens to a flat neutral instead, since a washed-out brand green still reads as "branded," while flat neutral reads unambiguously as "not interactive."
- `color.surface.overlay` (the modal/dialog scrim) — the roadmap flagged this as needing a real decision, since Token Foundation's primitives are all opaque. Resolved with CSS `color-mix(in srgb, {color.neutral.12} 60%, transparent)` at the semantic layer, rather than adding a new alpha-channel primitive to Token Foundation for a need that's really semantic-layer-specific.

**The big unknown, tested for real and genuinely important either way it went:** whether Style Dictionary's `outputReferences` option (set back in Token Foundation Chunk 01, never exercised until now) actually preserves token aliases as chained CSS `var()` references, or silently flattens them to literal values. It worked exactly right — `--ds-color-action-primary: var(--ds-color-brand-9);`, not a flattened hex — and even the `color-mix()` case correctly preserved the embedded reference inside the function call. This matters a lot: if it had silently flattened, every semantic token would quietly stop tracking its primitive, and nobody would notice until a rebrand shipped half-updated.

**A real architectural finding, not a bug — caught by actually comparing the CSS output against the TS output for the same token:** the TS constants *do* flatten to literal values (`export const ColorActionPrimary = "#193921";`), since TS has no equivalent of `var()`. This means **TS token constants can never participate in Phase 4's runtime brand/theme overrides** — a white-label override of `--ds-color-brand-9` propagates automatically to every CSS consumer of `var(--ds-color-action-primary)`, but anything that imported the TS constant instead is frozen at build time with zero relationship to any later override. Saved to project memory as a hard rule for Phase 5: theme-reactive styling must go through the CSS custom property, never the TS constant.

**Verification:** full fresh `build`/`lint`/`typecheck` across the workspace (25/25), plus a throwaway import of both a simple alias and the `color-mix()` overlay token from `packages/primitives`, reverted after — same pattern as every prior chunk.

**Why:** Token Foundation deliberately left "success" without a primitive scale — whether it reuses the brand green or gets its own hue was a semantic decision, not a primitive one. Decision: a dedicated hue, not a reuse.

**What we did:**

## Chunk 01 — Cascade layer structure

**Why, properly explained this time, not just "for precedence":** every token from Phases 2-3 currently sits in one flat `:root` block. With no `!important` and everything using the same selector, precedence between any two conflicting declarations is decided by exactly one thing — which line comes later in the generated file, which itself is just an accident of Style Dictionary's file-glob order, not a deliberate decision. CSS Cascade Layers invert the normal rules entirely: **layer order beats specificity, unconditionally** — a rule in a later-declared layer wins even against a far more specific selector in an earlier layer. That matters concretely here: once Phase 5 writes real component CSS, a component's own selector will almost always be more specific than a theme override like `[data-theme="dark"]`. Without layers, the component would win that fight by accident, regardless of which one is *supposed* to win by architectural design (Primitive → Semantic → Brand → Theme → Component, fixed back in the System Blueprint). This had to be Chunk 01, structurally, not just first-by-convention — every later chunk's output only means anything in terms of a layer this chunk builds.

**What we did:**
- Confirmed by testing, not assumed: Style Dictionary's CSS formatter has no native concept of `@layer` — it only emits a flat `:root` block. Resolved by splitting the CSS platform into two intermediate files (`_primitive.css`, `_semantic.css`), filtered using Style Dictionary's own `token.filePath` metadata (any `tokens/semantic-*.json` source is semantic tier) rather than a hardcoded category-name list that would silently go stale the next time a token category gets added.
- A new script, `scripts/assemble-layers.mjs`, wraps each intermediate file's already-correct output in its `@layer` block and writes the final `tokens.css` — a text-level wrap around Style Dictionary's proven-correct formatter output, rather than reimplementing it from token objects (lower risk of regressing the `outputReferences`/composite-type behavior already proven in Phase 3).
- Verified every cross-layer reference survives correctly by reading the real assembled file — `color.surface.base` in the semantic layer still correctly resolves to `var(--ds-color-neutral-1)`, a variable defined in the *earlier* primitive layer, which is fine: CSS custom properties resolve at use time regardless of which layer defines them.

**A real bug caught by the verification itself, unrelated to layers:** manually running Stylelint against the assembled output (to confirm it's syntactically valid CSS, since no browser-automation tooling exists yet — see below) surfaced something that's been silently sitting in `build/` since Semantic Layer Chunk 04: the shared config's `value-keyword-case` rule would lowercase `SFMono-Regular`/`Menlo`/`Consolas` in the mono font stack, which would actually *break* font matching, since those are proper font names, not CSS keywords. Never caught before because `build/` output is normally excluded from lint entirely. First fix attempt didn't work — `ignoreProperties: ["/^font/"]` doesn't match `--ds-font-family-mono`, a *custom property*, since the pattern was anchored to the start and the token has a `--ds-` prefix. Fixed by matching `/font-family/` anywhere in the property name instead, then confirmed a genuine casing violation elsewhere is still caught — the fix narrows the rule correctly rather than quietly disabling it.

**An honest scope limit, stated plainly rather than glossed over:** the original plan for this chunk included a live-browser test proving a later, lower-specificity layer actually beats an earlier, higher-specificity one — not just correct-looking generated CSS. No browser-automation tooling (Playwright or equivalent) exists in this project yet, and that's deliberately Phase 11's job, not something to bring in as a one-off dependency for a single check here. What's actually verified now: the CSS is syntactically valid per a real parser, and every reference resolves correctly by inspection. The actual mechanism-level proof is deferred to Chunk 04, which already needs real-browser verification for its own reasons (the first genuine runtime-behavior test in this project) — so it's not skipped, just carried by the chunk that was already going to need a browser.

**Verification:** full fresh `build`/`lint`/`typecheck` across the workspace (25/25, zero warnings beyond the expected/investigated Style Dictionary reference notice).

## Chunk 02 — Dark-mode primitive color scale

**Why this has to be new primitive values, not a semantic-layer override:** every semantic token (`surface.base`, `action.primary`, ...) aliases into the single primitive scale built in Phase 2, which was only ever tuned for a light background. The semantic *names* are deliberately mode-agnostic (`action.primary` should always mean "step 9 of the brand scale," light or dark — that's the whole point of the Primitive → Semantic tier split in System Blueprint §05), but the primitive *values* those names point to have to change completely, because the design job each step does changes with the surface it sits on: step 1 has to become a near-black app background, step 9 has to stay legible and clickable against that near-black surrounding, step 12 has to become readable light text. None of that existed yet, so it has to land as new primitive-tier tokens, and it has to land before Chunk 03 (mode-switching wiring) — you can't wire a selector to switch to values that don't exist.

**Why "independently tune, don't invert" is the actual engineering risk (per the Blade comparison notes already in project memory):** naively reversing the light arrays breaks two things:
1. **Chroma doesn't survive inversion.** The sRGB gamut narrows sharply near L=0 and L=1, at different rates for different hues. The light scale's chroma curve was shaped for the light end of that boundary; the same numbers at inverted (low) lightness make `clampChroma` clip several steps far harder than their neighbors — an abrupt, invisible-in-the-source-numbers desaturation jump. That's the literal "generator-seam" bug class flagged from Blade's implementation.
2. **The brand anchor's role inverts.** `#193921` is dark; it works as light-scale step 9 because it's dark-on-light. The same hex as dark-scale step 9 would be a near-black solid on a near-black background — illegible. Dark step 9 needs a lighter, more vivid tint of the same hue instead.

**What we did:**
- Extended `generate-scale.mjs` with a `requestedC` vs. `actualC` (post-`clampChroma`) diagnostic on every generated step, printed as a "clamp-seam check" — this is the concrete, scriptable version of "don't just eyeball it," specifically built to catch the bug class above instead of relying on visual inspection.
- Hand-tuned independent lightness/chroma curves per family for a dark viewing context — step 1 lands at L≈0.15 (not L≈0: pure black causes halation/OLED smearing), step 12 lands at L≈0.92-0.94 (not L≈0.995: pure white text on dark is harsh, a known dark-UI convention). Brand's dark step 9/10 are deliberately elevated in lightness relative to the rest of that family's curve, unlike the light scale where the anchor sits at the family's natural dark end.
- Output goes to a **new, separate file** (`tokens/color-dark.json`, families named `brand-dark`, `neutral-dark`, etc.) rather than into `color.json` under a DTCG "mode." How these values actually get *selected* at runtime — Style Dictionary modes vs. a manual selector-scoped tree — is the explicit open unknown for Chunk 03, and generating values shouldn't prejudge that mechanism.
- Added a second contrast check against a **dark** surface (`neutral-dark` step 1/2) instead of white, plus a non-text 3:1-guideline check for each family's solid step-9 action color against the dark page background — the light scale's checks were all against white, which is meaningless for a dark scale.

**A real seam, caught by the new check, not the eye:** `danger-dark` (red, hue 27°) held chroma high through step 11 (~0.11, essentially unclamped) then requested 0.07 at step 12 — actual chroma fell to ~0.035, a 68% single-step drop, because red's sRGB gamut ceiling collapses much faster near white than near mid-lightness. Every other family's step 9-12 taper was gradual (each step a bit more clamped than the last, no isolated cliff); this one wasn't. Fixed by requesting values close to what the gamut can actually deliver at each step (`[.175, .125, .08, .05]` instead of `[.175, .16, .11, .07]`) so the taper is smooth by construction instead of by luck — verified numerically (drop is now ~56%, in line with the other families' tails) rather than by eye, since there's still no way to actually *see* these colors rendered in this project yet.

**A bonus finding, disclosed rather than quietly fixed or quietly ignored:** the same clamp-seam check, run against the *already-shipped* light scales as a regression guard, found `warning` and `success` also clamp 13-26% across steps 9-12. Checked the actual (not requested) chroma sequence by hand for both: it's a smoothly accelerating taper approaching a real gamut ceiling — no isolated jump — so this is the expected, physically-grounded behavior the check is supposed to tolerate, not a bug. Left unchanged; noting it here so the reasoning is on record instead of silently re-litigated later.

**Still an open honest gap, same shape as Chunk 01's:** every contrast/smoothness claim above is verified numerically (WCAG math, requested-vs-actual chroma), not by looking at rendered pixels — there's still no browser tooling in this project to actually *see* the dark scale on a screen. Carried forward with the same deferral as Chunk 01's live-layer proof.

**Verification:** ran the generator directly and read its diagnostic output for real (not just checked exit code); confirmed `color-dark.json`'s structure by reading the file; full fresh `turbo run build lint typecheck --force` (25/25); re-ran the same manual Stylelint-against-`build/` check from Chunk 01 against the new output — clean, no new casing or syntax issues from the new tokens.

## Chunk 03 — Theme-level value switching

**Why this was flagged as the biggest unknown in the whole phase:** every semantic token from Phase 3 has exactly one value today. This chunk makes each one resolve differently depending on `data-theme`, and *how* that gets built has real architectural weight — DTCG has a "modes" concept for exactly this, but whether Style Dictionary actually resolves it into usable CSS was never something to assume, it had to be tested.

**Resolved, and it went two layers deeper than expected:**
1. Grepped the installed Style Dictionary 4.4.0 package directly for any "mode" handling — zero references anywhere outside an unrelated example file's service-worker boilerplate. Confirmed: no native mode support at all, not even partial.
2. The manual fallback (a separate dark semantic token source) turned out to need more than a third output file on the existing config. Style Dictionary resolves every sourced file into **one token tree** before any formatting happens — `color.surface.base` defined identically in both `semantic-color.json` and `semantic-color-dark.json` produced **93 real token collisions** the moment both were loaded together, found by actually running the build and reading the crash, not predicted from reading the API. A CSS-output filter can't fix a collision that happens at the data-resolution stage, before any filter runs.
3. Fixed by splitting into two fully independent Style Dictionary instances (`style-dictionary.config.mjs` now exports `lightConfig`/`darkConfig`, run by a new `scripts/build-tokens.mjs` via the JS API instead of the CLI) — the dark instance's `source` never includes `semantic-color.json` at all, so the identical token path is only ever resolved once per build. Getting there took a second wrong assumption first: tried excluding the dark file from the light build with `"!tokens/semantic-color-dark.json"` in the `source` array, which did nothing — Style Dictionary runs each `source` array entry through `globSync` independently and concatenates the results; there's no negation semantics, a leading `!` is just a literal pattern matching nothing. Fixed by computing the light build's file list with `readdirSync` at build time instead (every `tokens/**/*.json` file except the dark one) — still not a hand-maintained list, so a future new token category file is picked up automatically.
4. `scripts/assemble-layers.mjs` extended to read the dark build's output and wrap it in `@layer tokens.theme { [data-theme="dark"] { ... } }`. Deliberately **no** `[data-theme="light"]` restatement — `tokens.semantic` already sets every property unconditionally, so if `data-theme` is absent or `="light"`, nothing in the theme layer matches and the semantic layer's value is simply what applies. A later layer with no matching selector can't win; restating light values here would be pure duplication with zero behavioral difference. This is a deliberate departure from the roadmap artifact's original exhibit, which sketched both blocks before this was actually built — updated the artifact to match what shipped, with the reasoning stated rather than silently changed.

**A real, load-bearing bug caught before it shipped, not a hypothetical:** two semantic tokens (`surface.overlay`, `text.inverse`) alias a primitive step for its *absolute lightness* (near-black, near-white), not its role-in-that-scale. A mechanical `neutral.N → neutral-dark.N` substitution silently inverts both, since the dark scale's step 1 is near-black and step 12 is near-white — the opposite polarity of the light scale. Checked each individually rather than assuming a single fix pattern covers both:
- `surface.overlay` — a scrim's job (dim/obscure) doesn't need to flip with theme, so it deliberately gets **no** dark override at all; the light-mode near-black value carries through unconditionally in both themes. Confirmed present exactly once in the final assembled CSS (in the semantic layer, not the theme layer).
- `text.inverse` — actually tested, not assumed by "role continuity" reasoning. First hypothesis (before checking numbers) was that the dark equivalent should be `neutral-dark.12`, the dark scale's own near-white/text step — that would have been **wrong**: computed real WCAG contrast against every dark-scale step-9 solid action color (brand/danger/warning/success, the colors `action.primary`-style tokens actually resolve to) and near-white text fails AA on all four (2.17–2.77:1), because Chunk 02 deliberately brightened dark-mode step 9 for legibility against a dark page — which flips which text polarity actually reads against it. Near-black (`neutral-dark.1`) passes comfortably on all four (5.59–7.16:1). The fix looks identical to the naive "just use step 1" guess, but was arrived at by checking real contrast numbers against real colors, not by a role-matching shortcut — worth recording precisely because the shortcut would have given the same-looking wrong answer with high confidence.

**A scope call worth stating explicitly:** the dark semantic tier gets no TS/JS constants, only CSS. Consistent with the standing project finding that TS tokens always flatten to literals and can't participate in a runtime theme switch — generating them for a tier nothing consumes yet would be speculative surface area with no current payoff. If a real use case for compile-time dark literals shows up later, this is a small, reversible addition, not a redesign.

**What we built:** `tokens/semantic-color-dark.json` (21 of 22 semantic color tokens — `surface.overlay` deliberately excluded), a two-instance Style Dictionary build (`build-tokens.mjs`, replacing the single CLI invocation), and a `tokens.theme` cascade layer containing exactly the deltas from the light default, verified by reading the real assembled `tokens.css` end to end — every property name matches its light-mode counterpart exactly (required for the cascade-layer override to work at all), every value resolves to the correct dark primitive, and `surface-overlay` appears exactly once, in the semantic layer.

**Still the same honest gap, now inherited by this chunk too:** this proves the CSS is structurally correct and every reference resolves, by reading the file. It does not prove a browser actually re-renders the right color when `data-theme` flips — that's still waiting on the first real rendered DOM, deferred to Chunk 04 along with Chunk 01's layer-vs-specificity proof.

**Verification:** ran the two-instance build directly and read the collision diagnostic and the intermediate `_theme-dark.css` before cleanup, to confirm the fix rather than trust a clean exit code; full fresh `turbo run build lint typecheck --force` (25/25); the same manual Stylelint-against-`build/` check from Chunks 01–02 (clean); confirmed `surface-overlay`'s single occurrence and the dark TS/JS exclusion by grepping the real generated files.

## Chunk 04 — ThemeProvider component

**Why this chunk is structurally different from everything before it:** every prior chunk produced *data* — correctly layered, correctly aliased CSS. Nothing yet decided what `data-theme` actually equals, or set it. This is also the first chunk whose deliverable is executable UI logic rather than build output, which changes what "verify it" means — every earlier chunk was proven by reading a generated file; this one had to actually run.

**Why the pre-paint bootstrap logic can't be a React effect:** React only runs after the browser has already parsed the document and started painting with whatever's in the markup. Setting `data-theme` inside `useEffect` leaves a real, visible flash-of-wrong-theme gap — not hypothetical: the Blade comparison found their own provider has a code comment admitting this exact gap is "a known SSR limitation... acceptable for the initial release," with zero mitigation anywhere in their codebase. `@farmsapp/themes` exports the bootstrap logic as a plain string (`getThemeInitScript()`), deliberately not owning the HTML document itself — Next.js, a Vite `index.html`, and a real downstream app each need it wired into `<head>` differently, and that's each consumer's concern.

**A real dependency decision, made with the user rather than unilaterally:** Chunks 01 and 03 both deferred their live-browser proof, explicitly landing it here since this is the first chunk that renders anything. Full Playwright (bundled Chromium, ~300MB) felt like the same disproportionate weight already declined twice before. Flagged a lighter alternative — `playwright-core` (a thin CDP client, no bundled browser) driving the Edge already installed on this machine — and asked rather than deciding alone, since it's a real new-dependency call with a genuine trade-off, not a judgment call within already-agreed scope. Chose the lightweight path.

**A real correctness bug, caught by actually building the package, not by inspecting source:** Rollup silently drops module-level directives (`"use client"`) when bundling — confirmed by reading the actual compiled output file, where the directive was simply absent, not misplaced. This would have shipped a package that builds clean but breaks the instant Next.js App Router imports it (a hooks-using component with no client-boundary marker). Fixed with `rollup-plugin-preserve-directives`, added to the shared `tooling/build/rollup.config.base.mjs` so every future package gets this for free, not just this one. Verified the fix for real, not just by re-running the build and eyeballing the diff: temporarily wired `ThemeProvider` into `apps/docs`'s actual root layout (a Server Component) and ran a real `next build` — compiled clean, and the server-rendered HTML output was inspected directly to confirm the inline bootstrap script actually lands in `<head>`, verbatim, before body content. Reverted the probe afterward (dependency, layout.tsx, lockfile) — kept only the real fix (the plugin) and the real package.

**What we built:**
- `bootstrap.ts` — `getThemeInitScript()` (synchronous, try/catch-wrapped, reads `localStorage` then falls back to `prefers-color-scheme` then light) and the shared `THEME_STORAGE_KEY`.

## Chunk 05 — Brand-override axis

**Why this is the real test of the whole phase's core bet:** Cascade Layers were chosen back in Token Foundation Chunk 01 specifically to make white-label overrides structurally safe. That's been proven for theme switching (Chunk 04, live). It had never been tested for the thing it was actually chosen for until this chunk.

**A real design tension, caught by reasoning before writing any code, then verified rather than trusted:** the five-layer order is fixed (`tokens.brand` before `tokens.theme`). Overriding a *semantic* token (`--ds-color-action-primary`) in the brand layer would be silently clobbered the moment dark mode is active, since `tokens.theme`'s dark declaration for that same property is in a later layer and always wins regardless of what the brand layer said — the exact mechanic proven live in Chunk 04, now working against the goal instead of for it. Written up as this project's first `decisions/decision-*.md` (a new standing practice, starting this chunk): [`decision-brand-override-targets-primitives.md`](../decisions/decision-brand-override-targets-primitives.md). The fix isn't a workaround, it's a property of how `var()` actually resolves: a custom property reference resolves against whatever that property's cascaded value *currently is* at paint time, regardless of which layer either side was declared in. Targeting the *primitive* variables (`--ds-color-brand-9`, `--ds-color-brand-dark-9`) instead of the semantic ones means every downstream reference — in both themes — picks up the override automatically, and brand's fixed earlier position in the layer order stops mattering, because the override never has to win a layer fight against theme at all.

**What we built:**
- `tokens/brand-pilot.json` — a clearly-synthetic pilot brand (hue 320°, nowhere near the real brand's ~150°), overriding only the two steps (9, 10) any semantic token actually references, in both light and dark context. Computed via the same OKLCH methodology as the real brand family (reusing its exact L/C targets, just at a different hue), not hand-picked hex values.
- A third independent Style Dictionary instance (`brandPilotConfig`), same structural reason as Chunk 03's dark tree: `color.brand.9` in `brand-pilot.json` deliberately collides with the real `color.json`'s path, so it needs total source-tree isolation. `build-tokens.mjs` now runs three instances; the light build's computed file list excludes both isolated-tree files, not just the dark one.
- `assemble-layers.mjs` extended to wrap the pilot output as `@layer tokens.brand { [data-brand="pilot"] { ... } }`, positioned between `tokens.semantic` and `tokens.theme` — though (documented directly in the script) only the bare `@layer` declaration line actually fixes precedence; a layer's position is set wherever its name is *first* mentioned, so the populated block's physical position in the file is for readability only.
- `ThemeProvider` extended with `brand`/`setBrand` (typed `string | null`, deliberately not a literal union of known brand ids — owning a brand registry is Phase 12's job, not this package's). The bootstrap script now also restores a stored brand pre-paint. No `matchMedia`-style system-preference fallback for brand — there's no OS-level signal for "which white-label brand," so absent an explicit choice, no attribute is set at all, and the default primitives simply apply.

**Proven live, against real computed values, including the specific test this chunk exists to pass:**
- `data-brand="pilot"` alone (light theme): `action.primary` changed from `rgb(25, 57, 33)` (`#193921`, the real brand anchor) to `rgb(62, 39, 67)` (`#3e2743`, the pilot's light step 9).
- An unrelated semantic token (`surface.base`) stayed byte-identical (`rgb(253, 254, 253)`) with the brand override active — "nothing that shouldn't change, does," verified, not assumed.
- **The critical cross-axis case:** pilot brand + dark theme together resolved to `rgb(187, 124, 202)` (`#bb7cca`, the pilot's *dark*-tuned override) — not `rgb(85, 174, 108)` (`#55ae6c`, the real brand's dark value, what a semantic-level override would have silently fallen back to). Also confirmed this differs from pilot+light's value, ruling out the dark override accidentally just reusing the light one. This is the decision log's claim, proven in a real browser, not just argued from CSS semantics.

**Verification:** real token build, assembled `tokens.css` read directly to confirm the brand layer's position and content; the same manual Stylelint-on-build check (clean); full fresh `turbo run build lint typecheck --force` (25/25); a real `playwright-core`-against-system-Edge session (reusing the Chunk 04 setup) with both a theme toggle and a brand toggle, five checks, all passing — probe reverted afterward (playground files, temp deps, lockfile resynced).

## Chunk 06 — Contrast validation

**Why "every `text.*` against its most likely `surface.*`" isn't actually a precise enough spec to implement directly:** a real UI doesn't pair colors by category name, it pairs them by *use* — button text sits on `action.primary`, not on any `surface.*` token at all; status text is either inline (on `surface.base`) or inside its own `-subtle` banner background, and those are two different real pairings with two different expected contrast numbers. Built the pairing table by actually reading what each semantic token's own `$description` says it's for (`success-subtle`: "Banner/toast backgrounds behind step-9 text or icons" directly names its pairing), not by pattern-matching category names.

**A real, previously-undetected accessibility bug, caught on the very first run of the checker:** `feedback.warning` (light mode, `#a46e00`) failed AA in three real pairings — as button text (`4.32:1`), as inline status text on the page background (`4.32:1`), and worst, against its own `-subtle` banner background (`3.56:1`, the furthest from passing). This traces to Token Foundation Chunk 03, which only ever checked contrast for the primitive scale's dedicated *text* steps (11/12) against white — never checked whether step 9 (reused as `feedback.warning`, a vivid "status" color, not a text color by original design) holds up when it's actually *used* as text or paired with its own subtle background. Fixed by shifting light `warning`'s steps 9–12 uniformly 0.10 darker in the OKLCH lightness curve (not just step 9 in isolation — a uniform shift preserves the existing inter-step deltas and the Chunk 02 clamp-seam-checked smoothness instead of risking a new seam by patching one step). Re-ran Chunk 02's own clamp-seam diagnostic after the change to confirm no new cliff was introduced (the increased clamping is a gradual taper, the same accepted pattern as the other status hues, not an isolated jump) — then re-ran the contrast checker to confirm the fix: 40/40 pairings pass.

**What we built:**
- `scripts/check-contrast.mjs` — resolves token references directly from the DTCG source files (not from generated CSS/TS output), by design: contrast math only needs final resolved hex values, and doing it this way means the checker doesn't need the dark/brand-pilot trees to have TS output, which they deliberately don't (see the TS-vs-CSS-vars finding from Phase 4's start).
- Four resolution contexts mirroring what the real cascade actually does at runtime: light, dark, brand+light, brand+dark — the last two built by overlaying the pilot brand's primitive overrides on top of the base primitive map before resolving semantic references through them, the same substitution the real CSS cascade performs.
- 17 pairings × the contexts where they actually differ (34 checks total, plus 2 informational-only `text.disabled` checks — disabled text is conventionally WCAG-exempt, printed but never gates the build).
- Wired into `pnpm build` as the first step (fail fast, and it needs no other build output to run) — a future value change that breaks contrast now fails the build loudly, not silently, matching the strict-value lint rule's philosophy from Phase 1.

**Verification:** ran the checker directly and read its real output (not just exit code) both before and after the fix; re-ran Chunk 02's clamp-seam diagnostic to confirm the retuned warning curve didn't introduce a new seam; full fresh `turbo run build lint typecheck --force` (25/25) with the contrast check now genuinely part of that chain, not just a script that exists.

## Chunk 01 — Utilities foundation

**Why:** `VisuallyHidden` and any accessibility-conscious primitive needs stable, unique DOM ids from the moment it exists — retrofitting that after Chunks 02-05 are built means touching every primitive twice. Every interactive component from Phase 6 onward needs the controlled/uncontrolled dual-mode pattern. Scope was corrected twice before this chunk even started (see the two entries above) — no `useFocusTrap`, no RTL utilities — so what actually got built here is smaller and sharper than the roadmap's first draft.

**What we built:**
- `useId` — a thin wrapper around `React.useId()`, not a hand-rolled implementation. The one real addition: accepts an optional caller-provided id, so a component can do "use what I was given, or generate one" without every call site reimplementing the same fallback. Deliberately skips the mistake Blade's own `useId` made (a reach-ui-derived hand-rolled version with a "migrate to React.useId after React 18" TODO that was never acted on) — this project is greenfield on React 18+, nothing to migrate away from later.
- `useControllableState` — hand-rolled, with the two escape hatches Blade's real, ~50-call-site usage confirmed as load-bearing rather than speculative: a `shouldUpdate` comparator (default reference-inequality) that can gate an update from applying at all, and a `skipUpdate` flag on the setter that updates state without invoking `onChange` (for syncing from something other than a user action without re-triggering the same handler). Both wrapped in a new `useCallbackRef` internal helper — needed so passing a fresh inline `onChange`/`shouldUpdate` every render doesn't defeat the setter's own memoization, a real footgun the naive version would have shipped with.

**Verified behaviorally, not just by type-checking — a plain hook still has real runtime logic worth proving, not just types:** wired a throwaway probe into `apps/playground` (four small widgets: uncontrolled, controlled, skipUpdate, shouldUpdate-gated) and drove it with the same `playwright-core`-against-system-Edge setup from Theme Runtime. Nine checks, all passing against real DOM text after real button clicks — including that controlled mode genuinely ignores `defaultValue` and tracks the external `value` prop, that `skipUpdate` updates state while genuinely suppressing `onChange` (not just "looks like it does" from reading the source), and that a custom `shouldUpdate` comparator can cap a value at 5 despite eight clicks trying to push it past. Probe reverted afterward (playground files, temp dependency, lockfile resynced).

**Verification:** real `pnpm build`/`lint`/`typecheck` of `packages/utilities` in isolation, then a full fresh `turbo run build lint typecheck --force` across the workspace (19/19).

**Correction, same chunk, prompted by the user pasting Blade's actual `useCallbackRef` source:** the first version above used a plain `useEffect` to keep the callback ref fresh. Real, working code, but not the most correct choice — Blade's real implementation uses `useInsertionEffect` (the earliest point React runs any effect, before layout and passive effects, specifically designed for this "keep a ref fresh before anything else runs" class of problem — React's own recommended pattern for approximating the experimental `useEffectEvent`), falling back through `useIsomorphicLayoutEffect` for environments where `useInsertionEffect` isn't available, itself falling back to plain `useEffect` on the server specifically to dodge a real console warning `useLayoutEffect` throws during SSR. Given this project's newly-confirmed requirement to power a real Next.js SSR app, that fallback chain stopped being a nice-to-have.

Rewrote `useCallbackRef` to match, and extracted `useIsomorphicLayoutEffect` as its own reusable utility rather than an inline detail — other primitives will likely need SSR-safe layout timing later (a Popover measuring its own size, for instance). Also adopted Blade's bundler-safety trick for accessing `useInsertionEffect` (an indirect property lookup rather than a direct `React.useInsertionEffect` reference, working around a real, reported webpack static-analysis issue) rather than inventing a different workaround.

**Verified two different things, honestly distinguished, not conflated:**
- A plain regression check (the same 9 `playwright-core` checks from before) confirmed the rewrite didn't break existing behavior — but this doesn't actually prove the timing fix *matters*, since by the time any click fires, all pending effects from the prior render have already flushed regardless of which effect hook was used. Said so plainly rather than claiming this test proved more than it did.
- What actually tests the real fix: a `react-dom/server` `renderToString` pass, with a negative control (a component calling `useLayoutEffect` directly) to prove the test could actually detect the warning it was checking for, not just that it happened to stay quiet. Real, concrete result: the negative control triggers React's actual "useLayoutEffect does nothing on the server" warning; the real `useControllableState`-based component does not.

**A real, unrelated bug caught while building that SSR check, fixed at the root:** the verification script crashed with `Cannot read properties of null (reading 'useState')` — two different React instances in play. Every library package (`utilities`, `themes`, `design-system`, `icons`) correctly declares a permissive `"react": "^18 || ^19"` peer range (the right call for a publishable library), but nothing forced a single concrete version across the workspace — pnpm had resolved `react@19.2.8` for isolated peer-only packages while the apps (pinned to `^18.3.0`) resolved `react@18.3.1`, two real copies coexisting. Wouldn't affect real published-package consumers (who bring their own single react instance), but is a real footgun for any workspace-internal testing that crosses package boundaries — likely to come up again given the SSR verification work ahead. ## Chunk 02 — Box

**Why:** every other Phase 5 primitive (Stack, Inline, Container, Text) is either Box or built on it — get its styling mechanism wrong once and the mistake ships in four more primitives before anyone notices. The roadmap deliberately left the runtime-vs-compile-time styling question open, committing to resolve it "with a real measurement, not a preference."

**Reconsidered the framing before building anything:** the three factors already pointing away from Blade's approach (its own real per-render cost, this project's low-end-device audience, Next.js SSR/RSC friction with styled-components' runtime `<style>`-tag injection) only rule out *styled-components-style* runtime CSS-in-JS specifically — not runtime styling in general. A simpler runtime option (React's native `style={{...}}`, no CSS-in-JS library) sidesteps the RSC friction entirely, since inline styles just serialize into HTML with nothing to collect. It was still rejected, for a reason specific to this project: inline styles can't contain `@media` conditions at all, which breaks the already-committed responsive-prop requirement. Landed on a fourth option the roadmap's original framing didn't consider: extend the existing, proven Style Dictionary pipeline to generate a small, finite set of utility CSS classes at token-build time, and have Box resolve props to class name strings instead of building any style object at render time. Full reasoning: `decisions/decision-box-atomic-css-over-inline-styles.md`.

**What we built:**
- `packages/design-system/src/atomicConfig.mjs` — the one place Box's prop surface is declared (which props exist, their CSS properties, their token-scale category). Both the CSS generator and `Box.tsx` import it, so the generated stylesheet and the component's className resolver can't drift apart.
- `scripts/generate-atomic-css.mjs` — reads real step names straight from `@farmsapp/tokens`' JSON source (spacing, semantic-color, breakpoint — never hand-listed, same "derive, don't hand-list" discipline as the tokens package's own build scripts) and writes `build/css/atomic.css`: 257 rules in the already-reserved `tokens.component` cascade layer, plus real `@media` blocks for responsive props.
- A dedicated `breakpoint.component` scale (`md: 600, lg: 1024`) — Box's responsive props needed one fixed scale bakeable into static CSS, and the existing `consumer`/`portal` breakpoints are a different concern (per-app page layout, not component props). `decisions/decision-component-breakpoint-scale.md`.
- `Box.tsx` — a typed style-prop surface (spacing, flex layout, semantic color, radius, border-width), polymorphic `as` rendering with a dev-mode-only allowlist warning (Blade's validated pattern), forwarding everything else through to the underlying element.

**The real measurement, and a real bug it caught:** built a throwaway benchmark (500 Box-density instances, 12 props each, `renderToString`, 20 iterations) comparing Box's atomic-class resolver against a naive per-render inline-style resolver mirroring Blade's own real (initially unmemoized) approach. First result: the naive version was *faster* — atomic classes measured 0.87-0.88x. Cause: Box's first draft looped its entire ~27-key prop schema every render checking each key against the actual props, instead of looping the props actually passed — the exact class of mistake already flagged in Blade's real code. Fixed by building one lookup `Map` at module load and iterating `Object.entries(props)` (bounded by usage, not schema size). Re-measured: 1.02-1.14x across three runs — parity, slightly ahead. Honest conclusion, written into the decision log: raw per-render JS cost isn't actually the deciding factor once both are implemented efficiently — the decision rests on what a timing loop can't show (real `@media` support, no runtime `<style>`-tag injection for RSC to conflict with, bounded CSS payload regardless of instance count).

**Two more real bugs, caught only by driving a real browser (playwright-core against the system Edge, throwaway probe wired into `apps/playground`, fully reverted afterward):**
- Box never rendered its children at all — `children` was in the "own props" set filtered out of what gets forwarded to the rendered element, and nothing added it back. Every Box rendered empty. Neither `tsc` nor `eslint` had any way to see this — a perfectly valid type, an empty `<div>`.
- `borderWidth="thin"` had zero visual effect — a real CSS behavior, not a bug in the generator: `border-style` defaults to `none`, and browsers compute border-width as 0 whenever style is `none`, regardless of the width value. Fixed (first pass) by bundling `border-style: solid` into the generated rule for both `borderWidth` and `borderColor` — later corrected, see the hardening pass below.

Both were caught by the real browser check this chunk's own decision log commits every future style-prop change to, not by the type/lint gate that passed cleanly on both bugs.

**Verified:** `tsc --noEmit` and `eslint` clean on `packages/design-system`; a real `pnpm run build` (generator + rollup); 11/11 real browser assertions (computed padding/background/radius/border-width matching their token values via a real `getComputedStyle` probe against a `div.style.color` trick — not string-matching CSS source; all three responsive breakpoint tiers confirmed by actually resizing the viewport; the `as` allowlist warning firing; the atomic stylesheet's `@layer tokens.component` wrapping present in the real served CSS); full fresh `turbo run build lint typecheck --force` across the workspace, 19/19.

**Hardening pass, same day, prompted by the user asking to stress-test Box before Chunk 03 builds on it:** built a permanent Box variant gallery in `apps/playground` — every prop, every value (all 12 space steps, all 6 radius steps, all 3 border-width steps, all 4 surface/3 border/4 text color tokens, all `display`/`flexDirection`/`flexWrap`/`alignItems`/`justifyContent` keywords, both responsive breakpoints, every allowed `as` tag plus one intentional disallowed one, a composed card example) — deliberately kept as a real fixture, not a throwaway probe, since `apps/playground`'s own stated purpose is exactly this and Chunks 03-04 inherit anything still wrong here.

Screenshotted both themes with `playwright-core` (not just rendered — actually looked at the images) and found two more real issues no automated assertion had caught:

- **No content was legible in dark mode unless it explicitly set its own `color` prop.** Not a Box bug — Box correctly does nothing you don't ask for — but a real, previously-invisible gap: nothing in this project sets a page-level default text/background color from the theme tokens, so any text relying on the browser's default black inherited color turned invisible against a dark `backgroundColor`. Left undecided, not answered by fiat.

**Prop rename, same day:** asked to rename the spacing props from short CSS-utility-style names (`p`, `pt`, `pr`, `pb`, `pl`, `px`, `py`, `m`, `mt`, `mr`, `mb`, `ml`, `mx`, `my`) to full words (`padding`, `paddingTop`, ..., `margin`, `marginTop`, ...) for IDE autocomplete readability. Turned out to be a pure data change, not a logic change: `atomicConfig.mjs` already kept a separate `prefix` field for the short string used only in the generated CSS class name (`ds-p-2`), so renaming the object key that Box's prop type and resolver both read generically left the generated CSS byte-for-byte identical — same 257 rules, same class names, confirmed by re-running the generator and diffing. `decisions/decision-box-prop-names-vs-class-prefixes.md`. `apps/playground`'s gallery updated to match and re-verified: same 7/7 assertions, same visual screenshots.

**Also answered: "why am I not getting prop suggestions for Box in main.tsx?"** First hypothesis (reasonable, but wrong): no TypeScript project references between packages (`"composite": false` in `tsconfig.base.json`), so `apps/playground`'s editor would be resolving `@farmsapp/design-system`'s types via the *compiled* `build/index.d.ts`, not live source. Set up `composite: true` + `references` across the workspace's `tsconfig.json` files on that theory — good monorepo hygiene regardless, kept — but re-ran the workspace `tsc --noEmit` and it still read the compiled output either way, so that wasn't actually the cause.

**The real cause, found while separately testing an unrelated thing:** passed a deliberately made-up prop name to a real `<Box>` usage as a sanity check and it typechecked with **zero errors** — the giveaway that `Box`'s prop type wasn't really being checked at all. Root cause: `React.forwardRef` can't be generic — `Box` was built as `forwardRef<HTMLElement, BoxProps<ElementType>>(...)`, which fixes the exact same wide `BoxProps<ElementType>` type for *every* `<Box />` usage in the app, since `forwardRef`'s type parameters are chosen once, at definition time, not per call site. Expanding `BoxProps<ElementType>` touches `ComponentType<any>` (part of `ElementType`, for custom-component `as` values), which drags an `any` into the union — and `SomeType | any` collapses to just `any` in TypeScript, a real, documented behavior, not a guess. So the *effective* prop type of `Box` everywhere was basically "anything goes" — explaining both the missing type errors (excess-property checking needs a real, non-`any` type to check against) and the missing autocomplete (VS Code suggests known members of the expected type; `any` has none to list). Fixed by building the real component under an internal name (`BoxImpl`) as before, then exporting `Box` as that value cast to a hand-written generic function signature (`<T extends ElementType = "div">(props: BoxProps<T> & { ref?: Ref<HTMLElement> }) => ReactElement | null`) — the standard workaround for this exact `forwardRef` limitation. Restores real per-call-site inference: `<Box padding="2" />` resolves `T` to `"div"`, `<Box as="button" />` resolves it to `"button"`, each producing a small concrete type instead of the `ElementType`-wide one. Re-ran the same fake-prop test against a freshly rebuilt `Box`: real error this time, on the identical input that previously passed silently. Full explanation with worked examples: `rca/rca-box-polymorphic-props-lost-type-safety.md` — the project's first RCA, a new sibling convention to `decisions/`, written for teaching rather than just recording the fix. Every future polymorphic-`as` component (Stack, Inline, Container, Text are all candidates) needs the same `forwardRef`-then-cast pattern or it silently reintroduces this exact bug.

## Chunk 03 — Stack, Inline, Container

**Why:** all three are thin, opinionated presets over Box — cheap to build now that Box's own API is proven; building any one of them before Box existed would have risked shaping Box's API around a single caller's needs. Blade has none of these (checked directly during the third Blade comparison, before Phase 5 started) — a deliberate deviation, not an oversight, since `packages/design-system`'s scope committed to these three by name back in Phase 1.

**What we built:**
- `Stack` — flex column, `gap` **required** (not optional, unlike every other Box-derived prop) — an unset gap silently defaults to 0 in CSS, which reads as "no spacing decision was made" when it's actually "someone forgot." Making the prop required turns the omission into a compile error instead of an easy-to-miss review comment.
- `Inline` — same shape, row axis, plus a simplified boolean `wrap` (not Box's real three-state `flexWrap`) — Inline answers one question ("should this reflow?"), the full three-state prop is still reachable directly through Box.
- `Container` — max-width + centering, using a brand-new dedicated token category (`tokens/container.json` → `container.maxWidth`, steps sm/md/lg/xl + a component-handled `full`) rather than reusing any existing breakpoint token set. Real design question, not mechanical: this project already has three different breakpoint-shaped scales (`consumer`, `portal`, `component`), and none of them fit — reusing consumer/portal would mean Container has to know which app it's in; reusing `component` conflates "when should this component's own props change" with "how wide should this page's content read," two genuinely different questions. Gave Container its own scale instead, same resolution as the earlier `breakpoint.component` decision. `decisions/decision-container-maxwidth-scale.md`.
- All three reuse the exact `forwardRef`-then-cast generic pattern from the RCA above, and Box's own value-scale types (`SpaceStep`, `Responsive<T>`, etc.) are now exported from `Box.tsx` rather than staying private, so Stack/Inline/Container don't redefine them.

**Verified the generic-cast pattern actually protects all three, not just Box:** ran the same fake-prop test from the RCA against Stack, Inline, and Container — all three correctly rejected a made-up prop name. Also used `@ts-expect-error` to confirm the *required* props (`gap` on Stack/Inline, `maxWidth` on Container) are genuinely enforced, not just documented — a build that no longer produces the expected error there would itself fail.

**A real bug found building Container, not a hypothetical:** every `maxWidth` step rendered at roughly the same ~90px width instead of the intended progressive widths. Checked computed styles rather than guessing from a screenshot: `max-width` was resolving correctly the entire time (640px, 768px, ...) — the token/var() plumbing was never the problem. Real cause: a flex item with `auto` side margins doesn't stretch to fill its container's cross axis by default (a real, spec-defined CSS behavior — auto margins override `align-items: stretch`), so Container shrank to its content's size and `max-width` never had anything wider than the cap to actually clip. Fixed with an explicit `width: "100%"` ahead of `max-width` in Container's own style — the same reason Bootstrap's `.container` class has always set `width: 100%` rather than relying on ambient stretch behavior, and it makes Container robust regardless of what kind of parent (flex, grid, block) it ends up inside.

**Verified:** `tsc --noEmit` and `eslint` clean on `packages/design-system`; a real `pnpm run build`; all three added to `apps/playground`'s Box variant gallery and driven with a real browser — Stack/Inline rendering correctly (including the wrap-vs-overflow visual difference), Container's five `maxWidth` steps confirmed via `getComputedStyle` at their correct, progressively wider computed pixel widths, correctly capped by available parent width where a step's value exceeded it; full fresh `turbo run build lint typecheck --force` across the workspace.

**A question raised while reviewing the token files, not something either of us had actually decided before now: why px, not rem?** Checked `decisions/` and this file — nothing addressed it; `px` was simply what Token Foundation used from day one, never a deliberate call. First pass: decided to keep everything `px`, reasoning that a `rem` value is only as trustworthy as the root font-size staying consistent across both apps this one shared package serves — real, but incomplete, since it doesn't actually argue against `rem` specifically for type.

**Corrected same day, after the user supplied Razorpay Blade's real RFC on this exact question** (`Units for typography and layout`, Feb 2021) — Blade's own conclusion wasn't all-`px`, it was a hybrid: typography `rem`, layout `px`. Their sharper argument: "everything `rem`" risks a real, specific failure — increasing font-size can shift which responsive breakpoint applies, since `rem`-based layout widths change along with the text, so a user asking for bigger text can silently get a *different layout*, not just bigger text. Type doesn't carry that risk (it reflows within its container rather than crossing a media-query threshold itself), so it gets the real accessibility win with none of the layout-breakage cost. Their RFC also directly verified something worth knowing plainly: browser zoom (Ctrl/Cmd +) stretches raw hardware pixels uniformly, unaffected by px vs rem — so WCAG's 200%-zoom criterion is satisfied by `px` content just as well; the real, narrower gap `px` alone leaves is specifically the *separate* text-size-only accessibility setting.

Revised to match: `typography.json`'s `fontSize` scale is now `rem` (same physical sizes at the standard 16px root — a unit change, not a resize); `letterSpacing` was already `em` and `lineHeight` was already unitless, both already correct. Everything else (`spacing`, `radius`, `borderWidth`, `focus.json`, `container.json`) stays `px`. Confirmed by grep this touches nothing already built — `Text`/`Heading` (Phase 5 Chunk 04) don't exist yet — and confirmed by rebuilding that the composite `text.*` tokens' `font` shorthand output picked up the new values automatically through their existing `{fontSize.700}`-style references, no other token file needed editing. Re-verified: tokens' contrast check (40/40, unaffected), full fresh `turbo run build lint typecheck --force` (19/19). `decisions/decision-rem-for-typography-px-for-layout.md`.

**One more piece of Blade, same conversation:** Blade actually stores typography tokens as bare *numbers* (`20`, not `"20px"`/`"1.25rem"`), with a small per-platform adapter function attaching the right unit at the point of consumption — their reason: web wants `rem`, React Native wants a raw unitless number, and a token pre-formatted with one unit can't cleanly serve both. Checked whether that reasoning actually transfers here rather than assuming it does: it does — Phase 2's own Blade-comparison notes above already name **Phase 11 (React Native parity)** as committed future scope, not speculative. Weighed adopting it now vs. deferring: the migration (bare numbers + a category-aware Style Dictionary transform reattaching `px`/`rem`) costs the same whenever it happens, since every component built so far only ever consumes the generated `var(--ds-*)` custom property, never the token's stored value directly — nothing gets cheaper by doing it early. Decided to defer to Phase 11 itself rather than carry adapter-pattern complexity through phases that have no second platform to justify it yet. `decisions/decision-unitless-tokens-deferred-to-phase-11.md` — written so Phase 11 planning doesn't have to re-derive this reasoning from scratch.

**A real bug in `atomicConfig.mjs`, found re-reading the file to explain it, not while building anything new:** the prop rename earlier in this chunk touched `SPACE_PROPS`' keys (`p` → `padding`, etc.) but missed one hand-listed array that duplicated those same keys separately — `RESPONSIVE_PROP_KEYS`, which controls whether `generate-atomic-css.mjs` emits `@media`-scoped rules for a prop. It still held the *old* short names after the rename. `Box.tsx` never actually reads this array (it independently marks every `SPACE_PROPS`/`KEYWORD_PROPS` key as responsive when it builds its own lookup `Map`), so Box kept emitting classes like `ds-p-4@md` exactly as before — but `generate-atomic-css.mjs`'s check (`RESPONSIVE_PROP_KEYS.includes("padding")`) now failed for every padding/margin prop, since `"padding"` was never in the stale array. Net effect: every responsive padding/margin usage of Box had rendered a class name with **zero matching CSS rule**, silently, since the earlier rename — confirmed against the real build output (`.ds-gap-2\@md` existed, `.ds-p-*@md`/`.ds-m-*@md` didn't; `gap`'s key was never renamed, so it never went stale).

The reason this slipped past the rename's own verification: that check confirmed the base rule count (257, unaffected — `RESPONSIVE_PROP_KEYS` only gates the `@media` blocks, not the base rules) and a visual screenshot, but never diffed the `@media` blocks specifically. A gap in *what* was checked, not in whether checking happened.

Fixed by deleting the hand-listed array and deriving it instead: `[...Object.keys(SPACE_PROPS), ...Object.keys(KEYWORD_PROPS)]` — the same "derive, don't hand-list" rule this file already applies to token step names, now applied to itself. This doesn't just fix the current drift, it makes the specific failure mode (a second copy of a key list going stale when the first one is renamed) structurally impossible here going forward. Rebuilt and confirmed `.ds-p-2\@md`/`.ds-m-2\@md` now generate; full `turbo run build lint typecheck --force`, 19/19. `decisions/decision-box-prop-names-vs-class-prefixes.md` updated with a "Follow-on bug" section rather than silently amending the original claim.

**Comparing `atomicConfig.mjs` against Blade's real `BaseBox` implementation, same day — dispatched a research prompt into a local Blade checkout asking it to trace the actual prop-resolution code, evidence-first.**

- **The architectural choice itself, validated with hard evidence, not just reasoning:** Blade's `BaseBox` is **100% runtime CSS-in-JS** — one function, `getAllProps`/`getBaseBoxStyles` (`baseBoxStyles.ts`), builds a styled-components `CSSObject` from props on every render (memoized via `useMemo`, keyed on a JSON-stringified prop dependency), fed straight into a `styled.div` template. There is no build-time CSS generation anywhere in Blade — no postcss step, no codegen script. This is exactly the mechanism Chunk 02's own decision log (`decision-box-atomic-css-over-inline-styles.md`) reasoned *away* from, on three grounds specific to this project (RSC/SSR friction, low-end-device render cost, real `@media` support needed). Now confirmed against Blade's actual shipped code, not just the general shape of styled-components: their real implementation pays exactly the cost our decision predicted, on every single `Box` render.
- **The exact bug I just fixed, present in Blade too — but papered over, not eliminated:** Blade's spacing scale itself is looked up dynamically (`getIn(theme, "spacing.3")`), so the *values* can't drift — same "derive, don't hand-list" discipline we already follow. But the human-readable pixel documentation is hand-duplicated as JSDoc comments across ~12 separate prop declarations in `spacingTypes.ts`, with an explicit maintenance comment acknowledging the risk: *"I wish there was better way to re-use jsdoc... we have to explicitly add docs to each prop... When you want to change a specific token value, you can select the entire block... and do find and replace."* This is the identical bug shape — a second, hand-maintained copy of information that already exists canonically elsewhere — that just broke every responsive padding/margin class here. Blade's resolution was to leave the duplication in place and ask future developers to remember a manual find-and-replace step; the fix applied here instead (deriving `RESPONSIVE_PROP_KEYS` from the same objects instead of hand-listing it) removes the duplication structurally, so there's nothing left for a human to forget. Worth remembering as a general rule, not just for this one array: **when the same real design system's actual production code carries a known, explicitly-commented instance of a bug class just fixed here, that's a strong signal the fix is a real improvement, not a stylistic preference.**
- **A genuine open gap, not yet decided:** Blade's `BaseBox` deliberately does **not** expose `className`/`style` props at all — a documented constraint (`rfcs/2023-01-06-layout.md`): *"a padding property on CSS can mess up the built-in spacing on a component."* Our `Box` currently does the opposite — any `style` prop a caller passes falls through to `rest` (nothing in `BOX_OWN_PROP_KEYS` claims it) and gets spread directly onto the rendered element, where inline-style specificity would silently win over any conflicting atomic class. Not fixed here — this is a real design decision (lock it down like Blade, matching their stated rationale, vs. keep the escape hatch, which `Container.tsx` itself already relies on internally for `maxWidth`) that affects every current and future Box-derived primitive, worth a deliberate call rather than a silent one-line change.

**Resolved the same day: locked `style` down, matching Blade.** `BoxProps<T>` now excludes `"style"` from what it inherits from the underlying element's own type, so passing it is a real compile error, backed by a dev-mode runtime warn-and-drop for any non-TypeScript caller. `className` was deliberately left alone — it's additive (a class can't retroactively cancel one of Box's own declarations the way an inline style can), so the specific risk Blade's RFC names doesn't apply to it the same way.

**A real complication, found by actually checking every current Box consumer rather than assuming the lockdown was a clean one-line change:** `Container.tsx` already depended on passing `style` straight through Box for its `maxWidth` mechanism (Chunk 03) — a legitimate, previously-verified use of exactly the capability being removed, and TypeScript has no notion of "this file is more trusted than that one" for the same exported prop type. Surfaced this to the user before implementing rather than picking a resolution unilaterally. Resolved with a second, deliberately differently-named prop: `unsafeStyle?: CSSProperties` on `BoxOwnProps` — functionally identical to the old `style`, but named to signal it's not part of Box's public contract. `Stack`/`Inline`/`Container` each explicitly `Omit<BoxOwnProps, "unsafeStyle">` in their own `OwnProps` interfaces, so extending `BoxOwnProps` wholesale (which all three do, for the rest of Box's prop surface) doesn't silently re-leak the escape hatch to app callers through a different prop name than the one that just got closed. `Container.tsx` switched its internal `maxWidth`/`width:100%` styling from `style` to `unsafeStyle`, and its own public `ContainerProps<T>` now excludes `"style"` too, closing the identical hole one level up. `decisions/decision-box-style-prop-locked-down.md`.

**Then a follow-up question surfaced a scoping myth, checked and corrected before anything was built on it.** Asked whether Box should let a consumer set an arbitrary `backgroundColor="red"` — and, secondhand, whether Blade's real answer to this is "Box is non-visual, `Card` owns all background/border/radius/shadow treatment." Rather than accept that recollection and start planning a `Card` component around it, dispatched a second evidence-first research prompt at the same local Blade checkout. **The claim didn't hold up:** Blade's real `BaseBox` carries `backgroundColor`/`borderColor`/`borderWidth`/`borderRadius`/`elevation` as genuine, documented public props from its own founding RFC — `Card` isn't a separate visual layer, it's `BaseBox` wrapped in one locked, non-configurable composite recipe (layered shadows + gradients) that a single prop combination can't reproduce, and `Card` even deprecated its own override props to no-ops to enforce that lock. Their `Alert` (the actual answer to "I need a red/error background") is itself just `styled(BaseBox)` with a feedback-colored `backgroundColor` set. Good moment to have checked rather than assumed: it validated the Box already built here (background/border/radius as real props) rather than undermining it, and corrected a plausible-sounding but wrong recollection before any code got written around it.

Two real, separate follow-ups came out of that same research pass, decided individually rather than bundled:

- **Feedback colors on Box's `backgroundColor`** (danger/warning/success, which already exist as Phase 3 semantic tokens) — Blade's own real precedent argues for eventually exposing them, since their `Alert` is built exactly that way. Decided to defer rather than add now: no `Alert`/`Banner` primitive exists yet to actually consume it, so extending `backgroundColor` today would be speculative. Revisit when that primitive is actually built (Phase 7+).
- **A real, evidenced gap: no runtime check on Box's color/radius/borderWidth prop values.** Blade's own public `Box` throws in dev mode when `backgroundColor` gets a non-token value (`validateBackgroundString`) — a genuine runtime guarantee beyond what TypeScript alone provides. Ours had none: a type-bypass or non-TypeScript caller passing an invalid value would silently produce a class name with no matching CSS rule, the identical failure shape to the `RESPONSIVE_PROP_KEYS` bug from earlier the same day, just reached through an unchecked value instead of a stale key list. Fixed by adding `warnIfInvalidTokenValue` to `Box.tsx`, checking `backgroundColor`/`borderColor`/`color`/`borderRadius`/`borderWidth` against the real, current token step lists — derived, not hand-listed a second time: `generate-atomic-css.mjs` already computes these exact lists to build the CSS itself, and now also writes them to a new generated module (`src/generatedValidSteps.mjs`, gitignored, paired with a hand-authored `generatedValidSteps.d.mts` — same convention as `atomicConfig.mjs`/`.d.mts`) that `Box.tsx` imports and checks against. Deliberately warns rather than throws, unlike Blade's version — consistency with every other dev-mode guard already in this file (the `as` allowlist, the dropped-`style` warning) mattered more here than matching Blade's exact behavior. Verified with a throwaway `renderToString` probe (deleted after): a deliberately invalid `backgroundColor="crimson"` produces exactly one warning, a valid `backgroundColor="raised"` produces zero. `decisions/decision-box-runtime-token-validation.md`.

**A structural question, same day, not really about Box's props at all: why does `atomicConfig.mjs` exist as a separate file when nothing like it exists in Blade?** Worth answering plainly rather than assuming the comparison itself was flawed: Blade genuinely has no equivalent, and that's not a gap in the research — it's the direct consequence of Blade resolving everything in one runtime function (`getAllProps`), with exactly one consumer of "what props exist, what CSS they map to." Our architecture has *two* consumers that both need to agree on Box's prop surface — `scripts/generate-atomic-css.mjs` (build-time, generates the real CSS) and `Box.tsx` (render-time, picks matching class names) — a structural situation Blade's runtime-only approach never creates in the first place. `atomicConfig.mjs` is the direct answer to that specific two-consumer problem, downstream of the earlier build-time-vs-runtime decision (`decision-box-atomic-css-over-inline-styles.md`), not a pattern borrowed from anywhere.

**That same conversation surfaced a real, forward-looking structural problem worth fixing immediately rather than letting it compound: `packages/design-system/src` had grown to nine files sitting flat at the top level** (`Box.tsx`, `Stack.tsx`, `Inline.tsx`, `Container.tsx`, `atomicConfig.mjs`, `atomicConfig.d.mts`, `generatedValidSteps.mjs`, `generatedValidSteps.d.mts`, `global.d.ts`) with no per-component grouping — tolerable at 4 components, not at the 100+ the roadmap actually commits to once tests and Storybook stories join each one. Restructured to one folder per component under `src/components/` (`Box/`, `Stack/`, `Inline/`, `Container/`, each owning its own files), matching Blade's own real, already-confirmed structure (`packages/blade/src/components/Box/BaseBox/...`, `.../styledProps/...`, `.../__tests__/...`) rather than an invented convention. `atomicConfig.mjs`/`generatedValidSteps.*` moved into `Box/` specifically, for the same reason established in the "why does this file exist" discussion — they're Box's own mechanism, not a package-wide concern, matching how Blade nests `styledProps/` under `Box/` rather than at `src/`'s top level. Future test files will use a `__tests__/` subfolder per component, matching Blade exactly, decided explicitly rather than defaulted to a colocated-sibling-file convention.

Done immediately, not deferred — the cheapest point this restructure will ever be, since nothing in `packages/design-system/src` had been committed yet and only 4 components existed. `scripts/generate-atomic-css.mjs`, `Stack.tsx`/`Inline.tsx`/`Container.tsx`'s import of `Box`, and `index.tsx`'s barrel export all had their relative paths updated accordingly; nothing outside the package needed to change, since every consumer (`apps/playground` included) imports the compiled public export, never these internal paths. Re-verified: full fresh `turbo run build lint typecheck --force` (19/19), and a real browser check confirmed byte-identical behavior to before the move (same swatch dimensions, same `margin=auto` centering, same inverse-swatch color, same root max-width centering). `decisions/decision-per-component-folder-structure.md`.

**Then: why is `atomicConfig` split into `.mjs` + `.d.mts` instead of one `atomicConfig.ts`?** First-principles answer, proven live rather than asserted: `atomicConfig` needs to be imported by two different runners — `scripts/generate-atomic-css.mjs` (plain `node`, no build step first) and `Box.tsx` (bundled by Rollup). Removing `atomicConfig.d.mts` and re-running `tsc --noEmit` produces a real, immediate `TS7016` error ("Could not find a declaration file for module") plus a cascade of six more errors everywhere `Box.tsx` reads a field off the now-`unknown`-typed config — proven by actually deleting the file and watching it fail, then restoring it and watching it pass again. Renaming the same file to a different basename (`atomicConfigTypes.d.mts`) reproduces the identical failure even though a valid declaration file is sitting right there in the same folder — proof this is TypeScript's exact-basename `.mjs` ↔ `.d.mts` extension-mapping rule (part of Node16/NodeNext/Bundler module resolution), not a folder-scan heuristic.

The follow-up question — why not just make it real `atomicConfig.ts` and skip the split entirely — led to a genuinely surprising result that **contradicts something said earlier in this same conversation** (that Node 24.19.0 "silently drops named exports" from a multi-export `.ts` file, attributed to an earlier session). Tested directly, twice, in the real package: copying `atomicConfig.mjs`'s real content into `atomicConfig.ts` unchanged, and separately a version using genuine `interface`/type-annotation syntax — both ran correctly via plain `node`, with `scripts/generate-atomic-css.mjs` pointed at the `.ts` file, producing byte-identical output (`257 base rules`, same as always). Checked whether that earlier claim was ever actually written into this file before treating it as something to correct — it wasn't; it only existed in a prior conversation's summary, not in any commit, so there was nothing on disk to walk back.

**Kept the `.mjs` + `.d.mts` split anyway, despite the test passing.** Node's native TypeScript support is explicitly experimental and only *strips* types — it never *checks* them, so running a `.ts` file directly with `node` would never catch a real type error there; that still needs a separate `tsc` pass regardless of which extension is used. And its behavior is a demonstrably moving target: something changed between whatever Node point release produced the original (now unreproducible) finding and `24.19.0` today, with zero code changes on our side to explain it. Betting the actual CSS-generation pipeline — something every contributor's machine has to run identically, indefinitely — on a still-evolving experimental runtime feature is a real, ongoing risk the plain-`.mjs`-plus-hand-written-declaration split simply doesn't carry; `.mjs` has behaved identically on every Node version for over a decade. Judgment, not a hard blocker — recorded as such rather than overstating it as settled fact either way.

## Chunk 04 — Text, Heading

**Why this one was flagged as the riskiest remaining Chunk 5 piece:** three real open questions, not just implementation of already-settled ones — how composite typography tokens actually get consumed (the `font` shorthand can't carry `letter-spacing`, a real CSS limitation confirmed back in Phase 3), the Devanagari letter-spacing risk flagged since Token Foundation, and font-loading/subsetting strategy. Told explicitly not to assume anything and to put every real decision in a decision file — so this chunk started with three genuine forks surfaced before any code, not silent defaults.

**Decision 1 — font loading, deferred.** Checked first, not assumed: grepped the whole repo for `@font-face`/`.woff2`/a Google Fonts link and found nothing anywhere — the actual mechanism for loading Noto Sans/Noto Sans Devanagari onto a page has never existed. Self-hosting with real subsetting is the option this project's own low-end-device/weak-connectivity constraint would favor, but it's a substantial task on its own (sourcing real font files, computing real `unicode-range` subsets, deciding where assets live, tuning fallback-face metrics per the Blade comparison's earlier findings) — deferred to its own future chunk rather than bundled into Text/Heading's actual API design. `decisions/decision-font-loading-deferred-to-later-chunk.md`.

**Decision 2 — explicit `lang` prop for script detection, narrowed to `"en" | "hi"`** (not an open BCP-47 string, matching this project's actual stated scope). Does double duty: drives the internal letter-spacing decision *and* sets the real HTML `lang` attribute (verified in a real browser: `getAttribute("lang")` returns `"hi"` on the rendered element). `letterSpacing` defaults to `"normal"` always — never applied implicitly by `variant` — and a shared resolver (`src/components/Box/resolveTypographyClasses.ts`, used by both `Text` and `Heading`) forces `tight`/`wide` back to `"normal"` and warns in dev whenever `lang="hi"`, rather than trusting every call site to remember the risk. Verified twice: a real browser check confirmed the *computed* `letter-spacing` for the unsafe combination resolves to `"normal"` (vs. `-0.16px` for a genuine Latin tight-tracking case — the real `-0.01em` token at a 16px base) — proving the guard changes applied CSS, not just logs; a `renderToString` probe (`NODE_ENV=development`, deleted after) confirmed the warning fires for exactly the two unsafe combinations tested and stays silent for the two safe ones. `decisions/decision-devanagari-letter-spacing-guard.md`.

**Decision 3 — Heading's `level` and `variant` are both required and fully decoupled, with no `as` prop at all.** `level` picks the real `h1`-`h6` tag (document structure); `variant` picks the visual style; no implicit mapping between them, no default for either — matches real accessibility guidance (heading hierarchy should reflect structure, not desired size) and mirrors the reasoning behind Stack/Inline's required `gap`. A real, incidental benefit: since `HeadingProps` carries no type parameter, `Heading` needs none of the forwardRef-then-cast machinery every other primitive requires — verified this wasn't just unnecessary caution by initially adding the cast anyway, then removing it after checking it actively contradicted the file's own header comment. Verified with `@ts-expect-error` (throwaway probe, deleted after): both `<Heading variant="display" />` and `<Heading level="1" />` genuinely fail to compile. Verified in a real browser: `level="2"` + `variant="display"` renders a real `<h2>` at `36px` (the `display` variant's actual size), while `level="1"` + `variant="heading-sm"` renders a real `<h1>` at `18px` — tag and visual size proven independently correct, not just type-safe. `decisions/decision-heading-level-variant-decoupled.md`.

**Decision 4 — `variant`/`letterSpacing` extend the same `atomicConfig.mjs` (as a new, separate `TOKEN_TYPOGRAPHY_PROPS` object), but stay off Box's own prop surface entirely.** Mechanically these compile to the exact same shape `TOKEN_SCALE_PROPS` already generates (one CSS property, a direct `var(--ds-{category}-{step})` reference) — confirmed against the real generated CSS for the composite `text.*` tokens (`--ds-text-display: var(--ds-font-weight-bold) var(--ds-font-size-900)/var(--ds-line-height-tight) var(--ds-font-family-body);`) before writing any config. Kept as a separate object from `TOKEN_SCALE_PROPS` specifically so `Box.tsx`'s `PROP_CONFIG` (built by iterating `TOKEN_SCALE_PROPS` directly) never sees these keys — merging them in would've been a JS-level backdoor around the TypeScript-level exclusion. The reasoning for excluding them from Box at all traces back to the same day's Blade `Box`/`Card` research: Box's real scope is layout + basic visual styling, and typography is `Text`/`Heading`'s own concern, same logic already applied to keeping feedback colors off `backgroundColor`. `decisions/decision-text-heading-own-typography-props.md`.

**A real class-name collision, caught before it shipped:** `variant`'s first draft used CSS prefix `"text"` — which silently collides with Box's *existing* `color` prop (also prefix `"text"`, for an unrelated concept). No visible bug today only because current step names don't happen to overlap — a "works by luck" gap, the same shape as two bugs already caught earlier the same day (`RESPONSIVE_PROP_KEYS`, the `borderColor`/`borderWidth` `border-style` bundling). Fixed by renaming to prefix `"font"` before generating a single colliding rule.

**A second real bug, caught by the exact same `renderToString` probe used to verify the letter-spacing guard, not a separate hunt:** every `Heading` render was triggering Box's own "disallowed tag" dev warning, because `h1`-`h6` were never in `ALLOWED_AS_TAGS`. Fixed by adding them — `Heading` is now precisely the "dedicated component" that warning's own message asks callers to reach for instead of raw `<Box as="...">`.

**Also caught during implementation, not left to reviewers:** `TOKEN_TYPOGRAPHY_PROPS`'s first `.d.mts` declaration used a loose `Record<string, ...>` type, which made every direct property access (`TOKEN_TYPOGRAPHY_PROPS.variant.prefix`) "possibly undefined" under this project's `noUncheckedIndexedAccess` — a real `tsc` error on the very next build, fixed by giving it an exact two-key shape instead (`{ variant: ...; letterSpacing: ... }`), since the object's real shape never varies the way `SPACE_PROPS`/`KEYWORD_PROPS` (many keys, always iterated generically) does.

**Full verification, same rigor as every prior chunk:** full fresh `turbo run build lint typecheck --force`, 19/19, after every real change (three times total across the collision fix, the `ALLOWED_AS_TAGS` fix, and the final state); a real browser check (`playwright-core`/Edge, both themes) added permanently to `apps/playground`'s gallery — `TextGallery`/`HeadingGallery` sections covering every variant, the letter-spacing guard, and the deliberately mismatched level/variant pairs — screenshotted and visually confirmed legible in both light and dark mode, matching the same dark-mode-legibility discipline established in Chunk 02's hardening pass.

## After Chunk 04 — a real "why did we need to touch Box for a Text change" question, and a genuine course-correction

Asked whether Text/Heading could show an arbitrary color at all, not just the 4-step `primary/secondary/disabled/inverse` scale — answered no, matching this project's own Stylelint raw-color rule and Blade's real `validateBackgroundString` guard, but noted the *real* underlying gap: feedback colors (danger/warning/success) already exist as real, contrast-checked Phase 3 tokens and weren't reachable from `Text`'s `color` at all. Computed real WCAG contrast (not assumed) for the candidate step — step 11 of each hue clears AAA (10-18:1) in both themes, vs. step 9's thinner AA-only margin (5.59:1 in dark) — and extended `color.text.*` with `danger`/`warning`/`success`, aliasing step 11 in both `semantic-color.json` and its dark override. Verified the theme-swap mechanism end to end: the real rendered computed color matched the exact expected hex in both light and dark mode.

**Then a direct, fair challenge: extending `Box`'s own `TextColor` type for a Text-only need — isn't that bad coupling?** Answered no at the time, reasoning that `color` was already a *shared* Box prop (not Text-specific), so extending its one definition was the correct place, unlike `variant`/`letterSpacing` which were deliberately kept off Box. That answer turned out to be built on an unverified assumption — asked to check it against Blade's real source rather than continue on priors, and the finding reversed it: Blade's `BaseBox` has **no text-color concept at all**, only `backgroundColor`/`borderColor`; `BaseText` declares an entirely independent `TextColors` type, with its own resolver, sharing nothing with `Box` except layout/spacing props. Said so plainly rather than defending the original answer — Blade wasn't precedent for "one shared color type," it was precedent for the opposite.

**Decided to restructure to match, not just note the discrepancy.** `color` moved out of `Box` entirely — out of `TOKEN_COLOR_PROPS`, into the renamed `TOKEN_TEXT_PROPS` (alongside `variant`/`letterSpacing`), with `TextColor` relocating from `Box.tsx` to `resolveTypographyClasses.ts`. `Text`/`Heading` gained `color` as their own declared prop (previously inherited for free through `BoxOwnProps`), kept genuinely optional with no default — unlike `variant`/`letterSpacing` — specifically so an unset `color` still lets ordinary CSS inheritance carry an ancestor's color through, preserving Box's old behavior exactly.

**The real cost of this, paid in full, not hand-waved:** `Box`'s `color` prop predated `Text`/`Heading` (Chunk 02) and was already used directly, with no `Text`/`Heading` involved, in nine places across the permanent gallery — `Section`'s title, `Label`, both `ColorGallery` demos, the `ComposedExample` card's title and body, and the gallery's own root wrapper and page heading. All nine migrated: `Section`'s title and the root heading became real `Heading`s (they were always semantically headings, using `as="h2"`/`as="h1"` as a workaround around not having one yet); `Label` and the card copy became `Text`; the root wrapper — which relies on `color="primary"` propagating through CSS inheritance to keep the *entire page* legible in dark mode — became `<Text as="div">`, since only `Text` can set that inherited color now that `Box` can't.

**A second, more serious bug, found while fixing the first:** removing `color` from `BoxOwnProps` did not make `<Box color="primary">` a compile error — it kept silently typechecking. Cause: React's own base `HTMLAttributes<T>` (in `@types/react`) declares a generic, non-standard `color?: string` attribute every HTML element inherits (listed under React's own literal "Non-standard Attributes" heading in its type definitions) — `BoxProps<T>`'s `Omit` excluded `"style"` explicitly but never `"color"`, so removing it from `BoxOwnProps` let it leak straight back in from React's own types, completely unvalidated. Worse than a type gap: it would have rendered as a literal HTML `color` DOM *attribute*, not a CSS style — which has no visual effect on a `div`/`span` at all, a silent, invisible failure. Caught only because a throwaway `@ts-expect-error` probe unexpectedly *passed* instead of failing — the exact discipline this project has leaned on all day (verify, don't assume the fix worked because the reasoning sounded right). Fixed by adding `"color"` to the `Omit` exclusion on `Box`, `Stack`, `Inline`, `Container` — `Text`/`Heading` needed no fix, since declaring `color` in their own `OwnProps` already excluded it via `keyof OwnProps`.

**One more, smaller self-inflicted bug along the way:** a doc comment explaining the fix above literally contained the string `@ts-expect-error` inside a plain `//` comment — TypeScript parses that pragma anywhere it appears at a comment's start, regardless of surrounding prose, so the comment itself became an "unused directive" error. Fixed by rewording, not suppressing — a reminder that this specific magic string isn't safe to reference literally in a real comment.

**Verified end to end, twice — once for the restructure, once for the `Omit` fix:** full fresh `turbo run build lint typecheck --force`, 19/19, both times. A real `@ts-expect-error` probe confirmed `Box`/`Stack`/`Inline`/`Container` genuinely reject `color` now while `Text`/`Heading` still accept it. A real browser check (`playwright-core`/Edge, both themes, full-page screenshots) confirmed every migrated usage renders with the correct computed color — title vs. body text distinguishably darker/lighter, the danger swatch still resolving to the exact `#720309` token value, the root wrapper's dark-mode legibility workaround still working identically through `Text` instead of `Box`. `decisions/decision-text-heading-own-typography-props.md`'s "Update" section has the full account.

## Text's API narrowed and extended, directly requested

Four separate, direct requests, taken one at a time rather than bundled into one guess:

**`as` narrowed from fully polymorphic to a closed 8-tag union** (`p`/`span`/`div`/`abbr`/`figcaption`/`cite`/`q`/`label`) and **`variant` narrowed from mirroring the token layer 1:1** (`body-md`/`body-sm`/`caption`) **to just `body`/`caption`** — the first token-backed prop in this codebase whose public values don't match its underlying token step names directly (`"body"` maps to `"body-md"` internally; `body-sm` stays a real, generated, currently-unreachable token). Dropping `as`'s genericity meant `Text` no longer needs the forwardRef-then-cast pattern at all — the same simplification `Heading` already got, for the same underlying reason (no per-call-site element type left to preserve once the tag set is closed). One real migration cost: `ComposedExample`'s card title used `<Text as="strong">` for semantic emphasis, and `"strong"` isn't in the new union — resolved with the new `weight="semibold"` prop instead of silently re-adding `"strong"` to the list.

**Four new props**, two of which needed a real technical correction before implementing, not a guess: the requested `textDecorationLine` union included `"dotted"`, which isn't a real `text-decoration-line` CSS keyword (that's a `text-decoration-style` value — shipping it as typed would have compiled fine and done nothing in the browser); and `wordBreak` was specified as raw `string`, unlike every sibling prop, which would let a typo typecheck and silently fail at runtime. Both surfaced and resolved with the user directly: `"dotted"` became a convenience value (applies `text-decoration-line: underline` *and* `text-decoration-style: dotted` together, via the same `extraDecl` mechanism `borderWidth`'s `border-style` bundling already uses), and `wordBreak` became a real closed union of the actual valid CSS values.

`weight` (token-backed, a new `TOKEN_TEXT_PROPS` entry reading real `fontWeight` step names) and `textDecorationLine`/`wordBreak` (fixed CSS keywords, no token meaning — a new `TEXT_KEYWORD_PROPS` object shaped like Box's own `KEYWORD_PROPS`, kept separate so `Box.tsx` never imports it, same reasoning as `TOKEN_TEXT_PROPS`'s own separation) both extend the atomic-CSS system. `truncateAfterLines` (a real per-instance number, not a token step) goes through `Box`'s `unsafeStyle` escape hatch instead — the standard `-webkit-line-clamp` pattern, the same mechanism `Container` already uses for its own non-token `maxWidth` styling.

**A real cascade-order question, verified rather than assumed:** `weight`'s `font-weight` and `variant`'s composite `font` shorthand both ultimately set the same CSS longhand — whichever rule appears *later in the stylesheet* wins, not whichever class appears later in the DOM's `class` attribute. Checked directly against the real generated CSS (`weight`'s rules land after `variant`'s, matching `TOKEN_TEXT_PROPS`' key order) before trusting it, then confirmed in a real browser: `<Text variant="body" weight="semibold">` computes `font-weight: 600`, not `body`'s own default `400`.

**Verified in a real browser, not just by reading generated CSS:** `weight="semibold"` computes `600` vs. `weight="regular"`'s `400`; `textDecorationLine="dotted"` computes as two genuinely separate CSS properties (`text-decoration-line: underline`, `text-decoration-style: dotted`); `wordBreak="break-all"` computes correctly; `truncateAfterLines={2}` produces a real measured element height of exactly `48px` — this variant's real line-height (`24px`) times 2 — despite the source text being many lines longer, confirming actual clipping, not just CSS properties being nominally present. Screenshotted the gallery's new demo rows and visually confirmed all three decoration lines distinct, weight increasing visibly, word-break wrapping differently per value. `apps/playground`'s gallery gained real demo sections for all four new props plus the narrowed variant list. Full fresh `turbo run build lint typecheck --force`, 19/19. `decisions/decision-text-as-tag-and-variant-narrowed.md`, `decisions/decision-text-additional-props.md`.

**The ripple this had into `apps/playground`'s permanent Box gallery, and why it had to be fixed rather than deferred:** 19 call sites in the gallery passed `style` purely for demo-sizing (fixed swatch widths/heights for visual comparison, `maxWidth`/`overflow`/`flex-shrink` for layout scaffolding) — every one of them stopped typechecking the moment `style` was removed from `BoxProps<T>`. Leaving the workspace in a state where `turbo run typecheck` fails isn't an acceptable stopping point given this project's own verification discipline, so this wasn't optional follow-up work — it was part of finishing the change. Migrated all 19 to a real stylesheet (`apps/playground/src/demo.css`, a small set of named, single-purpose classes like `.demo-w-240`, `.demo-h-90`) applied via Box's still-supported `className` prop — which is, not incidentally, exactly the pattern a real consuming app should already reach for once it needs something outside Box's token surface, now the *only* pattern available for it (rather than a special-cased escape hatch existing only in the demo). Re-verified with a real browser (`playwright-core`/Edge against a production `vite preview` build, not just dev mode): the 24px swatch still measures 24×24, the `margin=auto` demo still centers symmetrically (equal left/right gaps), the inverse-color swatch still resolves to the real brand hex (`rgb(25, 57, 33)` = `#193921`), the root's max-width centering still produces equal margins, and zero dev-mode "style prop dropped" warnings fire anywhere in the gallery — confirming no call site was accidentally left passing a stray `style`. ## Text gains `size` — a fifth prop that overrides one component of `variant`'s shorthand

Requested directly: `BaseTextSizes = "xsmall" | "small" | "medium" | "large" | "xlarge" | "2xlarge"`. Same underlying shape of question `weight` already answered (`variant`'s composite `text.*` token bundles a font-size into its `font` shorthand; `size` needs to override just that one component, standalone) — so it reused the identical mechanism rather than inventing a new one.

**No new pixel values were invented.** `typography.json`'s primitive `fontSize` scale already has 9 raw steps (100-900, 12px-36px), and every existing `text.*` variant already picks one. Rather than adding new numbers, `semantic-typography.json` gained a new `fontSize` object aliasing 6 of those 9 primitives under the requested names — chosen so each named size lines up with a font-size some real variant already uses: `xsmall`=12px (matches `caption`), `small`=14px (`body-sm`), `medium`=16px (`body-md`, Text's own default), `large`=18px (`heading-sm`), `xlarge`=20px (`heading-md`), `2xlarge`=24px (`heading-lg`). The two primitive steps between/beyond these (13px, and 30px/36px) were deliberately left unaliased — 13px has no existing anchor to justify a name, and 30px/36px stay heading/display-exclusive: a `Text` that large is a real "should this be a `Heading`?" decision, not a body-text sizing choice. `decisions/decision-text-size-prop.md` has the full mapping table and reasoning.

Implementation-wise, `size` is `weight`'s sibling in every way: a new `TOKEN_TEXT_PROPS.size` entry (`{ cssProps: ["font-size"], prefix: "font-size", varCategory: "font-size" }`), steps read from `semanticTypography.fontSize` (derived, not hand-listed) in `generate-atomic-css.mjs`, declared *after* `weight` in the object so its CSS rule lands later in stylesheet source order than `variant`'s own — same cascade mechanism already verified for `weight` beating `variant`'s `font-weight` component applies unchanged here for `font-size`. Text-exclusive, not added to `Heading` (same reasoning as every other Chunk 04 addition: `Heading`'s size already comes from its required `variant`, which has no safe default the way `Text`'s does).

**Verified in a real browser, not just by reading generated CSS:** all 6 `size` values compute their exact expected pixel value (`xsmall`→12px through `2xlarge`→24px). The cascade-order claim was proven directly, not assumed: `<Text variant="caption" size="xlarge">` computes `font-size: 20px` — `size` winning over `caption`'s own composite 12px — while a plain `<Text variant="caption">` with no `size` override stays at its own 12px, confirming `size` only takes effect when explicitly set. 288 base CSS rules now (was 282), 33 props total (was 32). Full fresh `turbo run build lint typecheck --force`, 19/19.

## `size` restructured again, this time to match a real trace of Blade's own Text — scoped per variant, not one flat scale

The user supplied a full component-anatomy trace of Blade's real `Text` (`Text.tsx`, `BaseText`, `getTextProps`, the type-level `TextProps<T>` conditional) and asked to stick to it. Comparing it against what had just shipped surfaced a real architecture gap: Blade's `size` isn't one flat scale usable with either `variant` — it's a discriminated union, `variant="body"` reaching a wider size range than `variant="caption"`, enforced at both the type level and (as a dev-only backstop) at runtime. Blade also unconditionally forces `weight` to `regular` whenever `variant="caption"`.

**Adopted, translated onto this project's own token scale rather than copied literally** (Blade's numeric step names don't correspond to ours): `TextOwnProps` became a real discriminated union, `TextBodyProps | TextCaptionProps`. Blade's dev-throw-with-prod-fallback — every other guard in this codebase (Devanagari letterSpacing, `warnIfInvalidStep`) warns and gracefully degrades, never throws; introducing the one throwing validator in the whole system wasn't worth breaking that consistency for a path only non-TypeScript callers ever hit. ## The BaseText comparison — two purposes already covered without the name, one real gap fixed

The user explained Blade's `BaseText`: the internal, unpublished renderer `Text`/`Heading`/`Display`/`Code` all share, justified by three purposes — (1) separating a raw styling surface from curated public props, (2) one shared place for cross-platform rendering, (3) using the `Text`-vs-`Heading` children-type split (`ReactNode` vs `string`) as a deliberate composition boundary. A first pass here went beyond that without fully committing to it: it added `aria-disabled="true"` on the link branch for `isDisabled`, while still leaving the click handler attached (since the gating variable already excluded `isDisabled` for links) — a link labeled disabled to assistive tech that was nonetheless fully clickable. This is exactly what broke a real Playwright verification pass: forcing a click past Playwright's own (correct) actionability refusal triggered a genuine navigation to `example.com`, stalling every subsequent check in that script. Fixed by matching Blade exactly — `aria-disabled` removed, `onClick` passed through **unconditionally** (Blade's `BaseButton` never gates it; blocking relies entirely on the native `disabled` HTML attribute's own browser-level behavior for `<button>`). The playground demo was relabeled to honestly reflect that `isDisabled + href` still opens, rather than implying it's blocked — matching Blade's own real, confirmed limitation rather than silently inventing a fix beyond it.

**Two real test-methodology traps, both isolated and confirmed as tooling limitations, not product bugs, before writing anything off:**
1. Reading a `:hover` background color immediately after `page.hover()`, with no wait, captured a mid-transition interpolated value (the CSS has a real 100ms `background-color` transition) — not a broken hover rule. Confirmed by re-reading after the transition settles: every variant's hover color matched its expected token exactly, in both themes.
2. `.focus()` (programmatic) does not reliably trigger Chromium's `:focus-visible` heuristic the way a real keyboard `Tab` does — an initial check read a focus outline color that turned out to be the button's own `currentColor` fallback (proving `:focus-visible` never actually matched), not the real `--ds-color-focus-ring` value. Fixed by driving focus with genuine `page.keyboard.press("Tab")` calls instead; the real outline color then matched exactly.
3. `:active` itself could not be verified this way at all — Playwright's synthetic `mouse.down()`/`mouse.up()` via CDP does not engage the browser's real `:active` pseudo-class, confirmed with a control test against a completely plain, unstyled native `<button>` with zero Button-specific CSS involved. Documented as a real, disclosed limitation (`decisions/decision-button-no-js-pressed-state.md`) rather than a false "verified" claim — high confidence by construction (same selector-writing pattern as the independently-verified `:hover`/`:focus-visible` rules) but not mechanically proven in this session.

**Disabled semantics, verified for real**: a disabled `<button>` genuinely blocks clicks (`pointer-events: none`, real `disabled` attribute, zero `onClick` fires even with a forced click) and is skipped by keyboard `Tab`; `isLoading`'s spinner overlay swaps in with zero layout shift (`getBoundingClientRect` identical before/after) and the button becomes genuinely disabled while loading.

**No JS `isPressed` state** — Blade's real `AnimatedButtonContent`/`useState` press-tracking exists specifically for React Native parity (no `:active` pseudo-class there); this project is web-only, so plain CSS `.ds-button:active { transform: scale(0.97); }` replaces it entirely, with no event-handler plumbing.

## IconButton — full Blade parity (emphasis + isHighlighted), zero new tokens

User explicitly chose full parity for this one, not a trimmed v1 — the real `emphasis: subtle | intense | moderate` (default `intense`) plus `isHighlighted` model, confirmed directly from Blade's real source and explanation pasted this session. Genuinely separate from `BaseButton`/`Button` throughout, matching Blade's own real structure: no shared internals, its own color model, its own default shape (transparent/unboxed unless `isHighlighted` or `emphasis="moderate"` requests a container), its own 3-step size scale (no `xsmall`).

**The real design puzzle was translating Blade's `interactive.icon[emphasis].*` token tree onto this project's much flatter scale without inventing a parallel token category speculatively.** Worked out cleanly by re-reading what `Button`'s own chunk had just added: `color.action.tertiary-hover` (`neutral.3`, "the subtle gray wash") turned out to be exactly the right semantic fit for `moderate`'s persistent background, and `color.action.secondary` (`neutral.4`) exactly right for `isHighlighted`'s hover-reveal background — a real, non-coincidental sign the token scale added for `Button` was already internally consistent, not tokens forced into service. Icon color itself just reuses `color.text.primary`/`color.text.secondary`/`color.text.disabled` directly (the same reuse `Icon`'s own `IconColor` already established). **Zero new tokens added for this chunk** — a genuinely different outcome from `Button`'s own chunk (which needed 6 new `action.*` entries), because `Button`'s variant colors needed real new *values* while `IconButton`'s emphasis model turned out to need only new *combinations* of values that already existed.

**Container gating is the one piece of real behavior worth calling out**: background/fixed-square presence is controlled *only* by `isHighlighted || emphasis === "moderate"` — plain `subtle`/`intense` (the common case) are fully transparent at every state, including hover; only the icon's own color shifts. This is a real, confirmed Blade behavior (`hasContainer` gates height/width/borderRadius in Blade's real source), not an assumption — and it's the reason `emphasis` and background presence are orthogonal concepts here, not the same axis.

**Blade throws for `size="large"` + `isHighlighted`/`moderate` (no large container exists); this project warns and degrades** — consistent with every other dev-mode guard in this codebase, never Blade's `throwBladeError`. Verified in a real browser that the fallback is genuinely clean: the button just hugs its icon's own intrinsic size (`width`/`height` both computed to exactly the icon's own pixel size, not a broken half-applied container class).

**A clean verification pass** — unlike `Button`'s own chunk (which caught two real bugs: a comment-embedded `*/` swallowing the entire base CSS layer, and an incoherent `aria-disabled`-without-blocking state), this chunk's real-browser check came back matching the design exactly on the first full run: all three emphasis colors correct in both themes at rest and on hover/focus-visible; `moderate`'s background persistent, `isHighlighted`'s background hover-only, plain `subtle`/`intense` never showing any background at any state; the `size="large"` guard firing its warning and falling back cleanly; disabled semantics correct (real `disabled` attribute, `pointer-events: none`, zero click fires even forced); and real keyboard `Tab` landing on an `IconButton` with the correct `:focus-visible` outline color. Reused the `Tab`-not-`.focus()` methodology already learned the hard way in the `Button` chunk, so no repeat of that particular trap this time.

`decisions/decision-iconbutton-separate-from-basebutton.md`, `decisions/decision-iconbutton-reuses-existing-tokens.md`, and `decisions/decision-iconbutton-dev-warn-not-throw.md` cover the full reasoning for this chunk. `Button`/`BaseButton`/`IconButton` — the three pieces the user asked for, matching Blade's real structure — are now all complete.

## Badge — single-file structure (no BaseBadge split), 4 real divergences from Blade

User asked for the same "trace Blade's real source first" discipline used for Button/IconButton. A full trace of Blade's actual `Badge.tsx`/`types.ts`/`badgeTokens.ts`/`getStyledBadgeStyles.ts` was gathered and pasted this session, plus its two siblings — `Counter` and `Indicator` — confirming Blade does **not** split Badge the way it split Button→BaseButton: all three are genuinely separate, unrelated components with no shared base.

**Every one of the 4 real divergences from Blade came from checking Blade's findings against what this project's own tokens actually contain, not from stylistic preference:**

1. **`color` prop, not `variant` — and only 3 values, not Blade's 6.** Blade ships `color: FeedbackColors | 'primary'` (5 feedback colors + a `primary` branch). This project's `semantic-color.json` only has 3 feedback roles (`success`/`warning`/`danger`) — checked directly, and confirmed the gap runs deeper than "not built yet": `color.json`'s primitive layer has exactly 5 hue families (`brand`/`neutral`/`danger`/`warning`/`success`), no blue/info-like hue exists at all. `neutral`/`information`/`notice` are blocked on a new primitive family, not just a new semantic pointer — flagged as a materially bigger lift than `primary`'s deferral (which only needs new pointers onto the *existing* `brand` scale). `color` ships required, no default, since every one of the 3 values carries real status meaning.
2. **Emphasis (`subtle`/`intense`) needed zero new tokens.** Blade's `feedback.background/text/icon.<color>.<subtle|intense>` role tree doesn't exist here — but `text.<color>` (step 11, already contrast-verified for colored text on light surfaces) and `text.inverse` (already used for text on solid Button backgrounds) turned out to be exactly the two values Blade's own tree would resolve to anyway. `subtle` = `feedback.<color>-subtle` bg + `text.<color>`; `intense` = `feedback.<color>` bg + `text.inverse`. One open item carried forward, not silently assumed fine: `text.<color>`'s documented contrast numbers were computed against `surface.base`, not against the `subtle` badge background specifically.
3. **3 sizes, not Blade's 4 — `xsmall` dropped.** Blade's `small`/`medium`/`large` (16/20/24px) map exactly onto this project's own `space.4`/`space.5`/`space.6`, but Blade's `xsmall` (14px) has no home here for two independent reasons: it would break the project's own 8px spacing grid, and `Icon` (from the Phase 7 Prerequisites chunk) was already fixed at 3 sizes with `small` (16px) as its floor — there's no smaller icon to put inside a 14px badge. Icon reuses `Icon`'s own `small` uniformly across all 3 Badge sizes rather than inventing a second Icon size to step between, at the cost of a known tight fit at `size="small"` (16px badge, 16px icon, ~zero vertical room) — left as a real, disclosed tradeoff to verify visually rather than solved preemptively.
4. **Warn-and-degrade, not Blade's `throwBladeError`, for empty/whitespace children** — the same standing project-wide divergence already established for `IconButton`'s size guard and `Button`'s accessible-name guard. The underlying rule matches Blade exactly (text required, no icon-only Badge — Badge has no `accessibilityLabel`-equivalent, unlike Button/IconButton), only the failure mode differs.

**A real simplification found only by re-reading `Button.tsx`'s own established pattern before writing `Badge.tsx`**: color is resolved entirely in `badge.css` (one class per `color`×`emphasis` combination setting both `background-color` and `color`), and `Badge.tsx` never passes a `color` prop to the nested `Text`/`Icon` at all — both already default to inheriting `currentColor` via ordinary CSS cascade (confirmed directly in `Text.tsx`'s and `resolveIconProps.ts`'s own doc comments), exactly the mechanism `Button`'s `button.css` already relies on. This is simpler than Blade's own approach (which resolves and threads an explicit color through `getColorProps` to both children) and needed no new code to achieve.

**Text truncation reused existing infrastructure with zero new code**: `Text`'s `truncateAfterLines` prop (built for `Heading`/`Text` generally, unrelated to Badge) already implements the exact `-webkit-line-clamp` technique Blade's own Badge uses — `truncateAfterLines={1}` was enough. Blade's companion `useTruncationTitle` hook (a `useEffect`-driven DOM-measurement pattern that adds a native `title` tooltip only when text actually overflows) was deliberately left out of this pass — a real, disclosed omission, not an oversight, since it's a genuinely separate piece of interactive behavior layered on top of the truncation Badge already has.

**Verification, with a real tooling gap surfaced honestly**: `tsc --noEmit` and `eslint .` both clean; `generate-atomic-css.mjs` regenerated with `badge.css` in its `componentCssFiles` list, confirmed present in the output bundle. The repo's already-running dev Storybook instance (started earlier in the session, outside this chunk) picked up `Badge.tsx`/`Badge.stories.tsx` live — `/index.json` confirmed all 8 stories registered with no build errors. No headless-browser tooling (`chromium-cli`, Playwright) was available in this environment to capture an actual screenshot, so real-browser visual verification (colors rendering correctly, icon fit at `size="small"`, truncation behavior) was **not** done this chunk and is called out as outstanding rather than assumed passing — Storybook is live at `localhost:6006` for a manual look.

**Two follow-ups added directly by the user mid-build, both now documented rather than left implicit:**

- **`shape?: "rounded" | "square"` (default `"square"`)** — a real, deliberate addition beyond Blade, which has no shape axis at all (always a fixed pill). `rounded` keeps Blade's own `radius.full` value as the non-default alternative; `square` (`radius.sm`, a softly-rounded rectangle) is the new default, which means every Badge's default look changed from a pill to a softly-rounded rectangle mid-session — a real visual change, not just an additive opt-in. Superseded the size-scale decision's "border-radius fixed at every size" claim into "fixed *per shape*, not overall" — `decisions/decision-badge-shape-prop.md` has the full writeup, and the size-scale doc was corrected to point at it.
- **User asked directly why `Badge`'s root is a raw `<span>` instead of `<Box as="span">`** — even though `span` is on Box's own allowed-tag list (unlike Button/IconButton, which are hard-blocked from Box by that same list). Answer, written up as `decisions/decision-badge-span-not-box.md`: the real dividing line in this codebase isn't "interactive vs. not," it's "does this component expose Box's own generic style-prop surface." `Stack`/`Inline`/`Container`/`Text`/`Heading` do and are Box-backed; `Button`/`IconButton`/`Spinner`/`Badge` have their own fixed, hand-written CSS and a closed prop surface, so Box's tag-validation/style-stripping machinery would be pure dead weight. `Spinner.tsx` (`<span role="status" className="ds-spinner">`) was the exact precedent confirming this wasn't a one-off choice for Badge.

**User pushed back on that answer with a concrete, real gap**: a consumer wanting `<Badge marginTop="...">` has to wrap it in a `Box` today, and asked for it to work directly across every non-layout component — then, correctly, asked for Blade's real answer before deciding how, rather than taking either side on reasoning alone. Blade's real source was fetched directly from `razorpay/blade` on GitHub this session (via the GitHub API's tree/raw-content endpoints, no auth needed for a public repo) rather than relying on memory of "how Blade generally works" — and it corrected the previous answer's edges rather than reversing its core: Blade's real `Badge.tsx`, `BaseSpinner.tsx`, and `BaseButton/types.ts` all intersect a real, curated `StyledPropsBlade` type (margin family + position/self-align/grid/flexWrap/visibility — 20 props, notably **excluding** padding/backgroundColor/borderRadius, which stay each component's own internal concern) and spread it via `getStyledProps(props)` onto an extra wrapper `BaseBox`. So Box-as-root was never actually the mechanism, even in Blade — a curated prop subset applied via a *second*, purpose-built wrapper was.

**This project's own architecture makes the wrapper unnecessary, and turns out to make this a genuine improvement over Blade, not just a port of it**: Blade needs a second `BaseBox` because its Box is a runtime styled-components layer requiring a real DOM node to attach a computed style object to. This project's Box only ever resolves to class-name strings, so the same margin classes (`.ds-mt-3`, etc., already shipped in `atomic.css` from Box's own usage — confirmed directly, no regeneration needed) can be concatenated straight onto the *same* root element each component already renders. Implemented via `Box.tsx`'s own already-exported `resolveBoxClassNames` — a seam its own doc comment had anticipated ("a future component that... still wants to accept Box-style layout props can resolve them to real class names... without duplicating this function") but that had sat unconsumed until now.

**Scoped to margin only, not Blade's full ~20-prop list** (`decisions/decision-margin-props-shared-across-components.md`) — same "don't build ahead of a real consumer" discipline as everywhere else in this session; no cited need yet for `position`/`zIndex`/`grid*`/`flexWrap`/`visibility` on `Button`/`IconButton`/`Spinner`/`Badge`. A new shared `MarginProps` type (`Pick<BoxOwnProps, ...>` the 7 margin fields) now sits on all 4 components — each destructures `...marginProps` and folds `resolveBoxClassNames(marginProps)` into its own existing hand-written class list. `VisuallyHidden` deliberately excluded (no real use case for margin on invisible content, and Blade's own real `VisuallyHidden` has no `StyledPropsBlade` either — consistent, not an oversight).
